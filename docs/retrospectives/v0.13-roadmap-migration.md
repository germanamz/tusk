# v0.13 Retrospective — ROADMAP.md Migration

> Date: 2026-04-27
> Initiative: ROADMAP.md Migration (v0.13)
> Status: shipped, cutover landed in `7526b27`

This is a process retrospective for v0.14 planning. The technical recap of
what shipped lives in the per-version status doc that lands when v0.13 is
released; this doc focuses on what the test harness and review process
*missed* and what to change before the next multi-phase initiative.

---

## What happened

The ROADMAP.md migration shipped clean across six phases (project
description field, markdown renderer, annotations/notes, cutover plumbing).
All phase-time tests passed. Post-implementation review reported zero
defects. The migration of 1039 tasks into the `tusk-roadmap` project ran
without surprises.

Then `make roadmap` was invoked for the first time against a populated
workspace, and **two latent defects surfaced at cutover** — neither caught
by the harness, neither caught by the post-implementation review:

1. **`tusk task tree project=<name>` rejected `project=…` as a filter.** The
   command treated it as a short_id, errored with "Task not found:
   project=tusk-roadmap." The design spec listed this exact invocation as
   one of the three valid `tree --format markdown` forms; the
   implementation never wired it.

2. **`make roadmap` truncated `ROADMAP.md` before checking command exit.**
   Shell redirect `> ROADMAP.md` ran first, so a failed render destroyed
   the source file. We rebuilt from `git checkout HEAD -- ROADMAP.md`.

Both fixed in `ceb41ee`. Cutover landed in `7526b27`.

## Why the harness missed them

### Bug 1 — the spec→phase translation gap

The design spec's §3.2 listed three valid invocations of `tusk task tree
--format markdown`. Phase 3's "user-visible behaviors (acceptance
criteria)" section listed two of them — the bare invocation and the
multi-project rejection — but **omitted the `project=<name>` form**. The
implementer wrote tests for what the phase doc asked for. The test corpus
honored the phase doc faithfully:

- `TestRunTree_MarkdownRejectsRollup`
- `TestRunTree_MarkdownRejectsMultiProject`
- `TestRunTree_MarkdownEmptyWorkspace`
- `TestRunTree_MarkdownSingleProject_StubOutput`
- `TestTreeMarkdown_FullDialect` (e2e)

Every one of those runs `tusk task tree --format markdown` with no
positional args. Inline-filter args on `tree` were never exercised because
nothing in the phase plan asked for them.

### Bug 2 — failure-path durability wasn't an acceptance criterion

Phase 6 specified the Makefile target literally as `tusk task tree
project=tusk-roadmap --format markdown > ROADMAP.md`. The implementer wrote
exactly that. Acceptance criteria covered the happy path ("succeeds against
a workspace where the tusk-roadmap project exists with at least one task")
and the error message ("produces an error message that points the user at
the manual migration workflow"). Neither asked **"and the prior
`ROADMAP.md` survives a failed render."**

Compounding: Phase 6's success path **could not be exercised at phase
time** because `tusk-roadmap` didn't exist yet — it only got created
during the user-driven manual migration *after* Phase 6 shipped. The end-
to-end smoke test for `make roadmap` was effectively deferred to the user.

### Why the post-implementation review missed both

The `phase-post-implementation-review` skill's checklist walks the *phase
docs* task-by-task and verifies each task maps to committed code. It does
not re-derive acceptance from the original design spec. I followed the
skill faithfully — and the bugs slipped through because the phase docs
were the gap.

## Process changes for v0.14

Three changes, ordered by leverage. The first one alone would have caught
both bugs.

### 1. Spec→test traceability matrix (highest leverage)

Before drafting phase plans, build a table that maps every concrete claim
in the design spec to where it gets tested. Every CLI invocation example,
every error message string, every "valid forms include..." list. The
matrix lives alongside the spec, not buried in phase docs.

For v0.13's renderer the matrix would have been:

| Spec claim | Test |
|---|---|
| `tusk task tree project=<name> --format markdown` valid | _(missing — Bug 1)_ |
| `tusk task tree <short_id> --format markdown` valid | covered |
| `tusk task tree --format markdown` (single-project) valid | `TestTreeMarkdown_FullDialect` |
| `--rollup` rejected | `TestRunTree_MarkdownRejectsRollup` |
| Multi-project tree rejected | `TestRunTree_MarkdownRejectsMultiProject` |
| Empty workspace emits nothing | `TestRunTree_MarkdownEmptyWorkspace` |

The empty cell on row 1 surfaces immediately. Continuity-review and
post-implementation-review both treat the matrix as the source of truth,
not the phase docs. Phase docs translate matrix rows into work; reviews
verify rows are covered.

**Action:** add a "build the traceability matrix from the spec" step to
`superpowers:writing-plans` before phase split. Make matrix completeness
a continuity-review gate.

### 2. Failure-path durability check on every state-mutating command

When a phase introduces a command that writes a file, mutates state, or
calls an external system, the per-phase verification gets a new explicit
check:

> *"If the command fails partway through, is the prior state recoverable?
> Is there a test that forces a failure and asserts the prior state is
> intact?"*

For `make roadmap` this would have asked: what happens when `tusk task
tree` errors? Is `ROADMAP.md` preserved? The answer would have driven the
tempfile+`mv` pattern at design time. This generalizes — atomic writes,
lock files, partial DB updates, half-sent messages.

**Action:** add a "destructive-action defensive pattern" category to
`phase-planning-rules` alongside "compilation safety" and "bridge code
tagging."

### 3. Forbid "deferred to user-driven validation" without a phase-time substitute

Phase 6's `make roadmap` validation was effectively "the user will exercise
this during migration." That's not validation — it's hope. If a feature
can't be tested at phase time because a prerequisite doesn't exist, the
phase must include either:

- a test fixture that creates the prerequisite (Phase 6 could have built a
  3-task `tusk-roadmap` fixture and run `make roadmap` against it), or
- a deferred-validation gate naming the *specific* phase where the test
  will run, owned by a named test.

"User will catch it during cutover" is a coordination failure, not a test
strategy.

**Action:** writing-plans skill rejects phase docs whose acceptance
criteria depend on user actions outside the phase sequence. If the phase
can't be tested at phase time, it must define the fixture or name the
follow-up phase.

## Smaller things that also help

- **Self-hosting in CI as a continuous test.** With the `roadmap-drift`
  CI gate now active, the gate itself is a continuous test of the
  renderer→file-write→diff loop. Bug 1 would surface the next time anyone
  touched the renderer. Already shipped in Phase 6 — value compounds as
  it stays green.

- **Parsers should fail loudly on ambiguity.** Bug 1 root-caused to:
  `tusk task tree project=tusk-roadmap` silently treated `project=tusk-
  roadmap` as a short_id, then errored with "Task not found." A stricter
  parser would reject `project=tusk-roadmap` as not-a-short-id and either
  succeed as a filter or error with "ambiguous: did you mean filter or
  short_id?" Loud failures point at root cause faster than silent
  reinterpretations. Worth auditing other commands that take positional
  short_ids for the same pattern (`task get`, `task modify`, `task
  done`, etc.).

- **Post-implementation review should re-derive from spec.** The
  `phase-post-implementation-review` skill currently walks phase docs.
  Adding a step that walks the design spec section-by-section and
  verifies each behavior was tested would have caught Bug 1 even without
  the traceability matrix.

## Recommendation for v0.14 planning

Pick up the traceability-matrix change first. It's a structural fix that
catches the largest class of bugs (anything in the spec that didn't make
it into a test) and costs almost nothing to maintain — the matrix is
written once during spec→phase translation and consulted by every
downstream review.

The other two changes are defense-in-depth. Worth landing, but their
incremental value drops once #1 is in place.

The bugs themselves are not interesting. The pattern is: **phase docs are
incomplete renditions of the spec, and reviews trust phase docs as
authoritative.** Until the matrix exists, every multi-phase initiative
risks the same shape of latent defect.

## Follow-up: e2e harness is not hermetic against walk-up config

While preparing this PR I tried to add a repo-root `tusk.toml` so that
`tusk` (and CI) could find `.data/tusk.db` via v0.9's walk-up config
discovery without an explicit `TUSK_DB` env. It broke the e2e suite —
tests run with CWD inside the repo, walk-up resolves the workspace
config as their active file, and tests that exercise `tusk config init
--local` / `tusk config set` wrote a full config dump back into the
committed `tusk.toml`. That polluted state then leaked into other tests
(e.g., a synthetic `[taxonomy]` section made the level-check tests fail
by demanding levels on `default`-project tasks).

Reverted on this branch. The right fix lives in the e2e harness:
isolate each test from walk-up by setting `TUSK_CONFIG` (the file, not
`TUSK_CONFIG_DIR`) to a per-test temp file, or by changing CWD to a
temp dir. With that in place, the workspace `tusk.toml` becomes safe
to commit and all the `TUSK_DB=...` plumbing in CI and contributor
docs goes away. Worth picking up early in v0.14 — the change is small
but each "edit roadmap → commit" cycle still pays the env-var tax
until then.
