# v0.13 Architecture Audit — Notes for v0.14 Planning

> Date: 2026-04-28
> Scope: read of the largest source files (`service/task.go` 2174L,
> `internal/mcp/tools.go` 1729L, `internal/tui/commands.go` 1450L,
> `internal/tui/render.go` 1231L, `sqlite/task.go` 709L, `cmd/tusk/main.go`
> 360L) plus a survey of `domain/`, `filter/`, `repository/`, and the
> v0.10–v0.12 status docs.
> Companion to: [v0.13-roadmap-migration.md](./v0.13-roadmap-migration.md)

This document collects observations on architecture, readability,
naming, performance, and long-term maintenance. It is forward-looking —
input for v0.14 planning, not an indictment of v0.13 work. Citations
use `file:line` so each claim points at the artifact that motivated it.

---

## Architecture

### 1. `TaskService` is becoming a god service

`service/task.go` is 2174 lines with 44 methods. One struct owns CRUD,
lifecycle (Start/Done/Delete/Complete), claiming
(Claim/Release/Pop/Available), urgency resolution, tree summaries,
project routing, and effective-weight stamping. Each addition was
locally reasonable; together they bury the lifecycle state machine
inside a soup of unrelated concerns.

The retrospective's "spec→test traceability" point applies here too:
when one struct owns 12 distinct behaviors, no review walks each
behavior end-to-end. Carve along the seams the test files already drew
— `task_claim_test.go`, `task_move_test.go`, `task_resequence_test.go`,
`task_urgency_overrides_test.go` — into `TaskClaimService`,
`TaskLifecycleService`, `TaskUrgencyResolver`. The `BundleResolver` /
`RepoBundle` plumbing makes splitting cheap; the constructor already
takes 6 dependencies, so the wiring cost is flat.

### 2. The pluggable multi-store story is half-built

`RepoBundle` and `BundleResolver` (`service/repos.go`) imply
per-project SQLite stores, but `List`, `Next`, `Pop`, `Available`, and
`bundleForShortID` all hardcode `defaultProjectID` → single bundle
(`service/task.go:296`, `:373`, `:1382`, `:1447`, `:110`). Either the
multi-bundle abstraction is paying for nothing (delete it; one DB), or
it's load-bearing for a future feature that has been deferred
indefinitely (commit to fan-out and add the missing tests).

Carrying the pattern as decoration is the worst option — every new
method has to choose, gets the choice silently wrong, and there is no
test that fans out. Pick a direction in v0.14.

### 3. Parser ambiguity surfaced once; audit before it surfaces again

Bug 1 in the v0.13 retrospective root-caused to `tusk task tree
project=tusk-roadmap` silently treating `project=tusk-roadmap` as a
short_id. The "audit other commands that take positional short_ids"
footnote in the retro is the right move — `task get`, `task modify`,
`task done`, `task delete`, `task start`, `task annotate`, `task
claim`, `task release`, `task link`, `task unlink` all take positional
short_ids per `internal/tui/commands.go:1064–1188`.

The fix is not 10 patches; it is one helper that classifies a
positional arg as `short_id | filter | ambiguous` and rejects ambiguity
loudly. Make `filter.Parse` of a positional return a typed verdict and
route every command through it.

### 4. Inconsistent batching across read paths

`listInBundle` batches relation/annotation/tag counts
(`service/task.go:325–339`) — good. But `Next` (`:373`) calls
`listInBundle` then loops calling `CountBlockedByTasks` per task to
find an unblocked one (`:397`). The blocking data is already in
`listInBundle`'s output via scoring weights but is thrown away.

Same shape in MCP's `projectNameCache` (`internal/mcp/tools.go:96`):
the cache exists because the surrounding code does N lookups; the
underlying repo could expose `GetByIDs(ids)` once. Pattern: caches and
batch helpers grow next to N+1 patterns instead of replacing them.

## Readability

### 1. `TaskService.Update` is 200 lines of nearly identical pointer-deref blocks

`service/task.go:890–1077` has the same `if upd.X != nil { task.X =
*upd.X }` shape repeated 12 times, with subtle variations for
double-pointers and nullable fields. A reader has to scan all 200
lines to confirm that each block is actually identical — the
variations matter.

This is the cost of double-pointer field updates. A small `applyField`
helper or codegen from a field-list would let the variations stand out
as the only thing they need to.

### 2. Big files mix abstraction levels

`internal/tui/commands.go` interleaves cobra command construction (the
380-line help string in `buildTaskCmd`), arg parsing, service calls,
and rendering. Split each verb's `runX` into
`internal/tui/commands/<verb>.go`; keep `commands.go` as registration
only. Same prescription for `internal/mcp/tools.go` — the JSON DTOs,
the per-tool handlers, and the registry of tool definitions all live
in one file.

### 3. The `taskJSON` / `taskResponse` / `treeNodeJSON` triplet drifts

`internal/tui/render.go`, `internal/mcp/tools.go`, and
`internal/tui/tree.go` each define a JSON shape for "a task." They are
90% identical and 10% different (urgency weights, rollups, claimed_by
surface area). When a new field lands on `domain.Task`, three places
need the corresponding JSON edit — and the test corpus does not
enforce that they stay in sync.

Either generate them from a single descriptor or have them embed a
shared `taskCoreJSON`. This is the same shape as the retrospective's
Bug 1: spec drifts because no single artifact is canonical.

### 4. The `domain` package has 36 files and is hard to map

`urgency_overrides_helpers.go`, `urgency_overrides_patch.go`,
`urgency_overrides_validator.go`, `urgency_overrides_validator_test.go`,
plus `resolved_urgency_weights.go` — five files for one concept.
Either fold into `urgency_overrides.go` or move into a `domain/urgency`
subpackage. Same opportunity for the taxonomy cluster (`taxonomy.go` +
`taxonomy_validator.go` + 3 test files).

## Function and variable naming

The codebase has a strong tendency toward single-character locals.
The "short body, short name" Go idiom is widely cited as a defense,
but it does not survive contact with this codebase: single-letter
identifiers are *harder* to scan, not easier, and the harm compounds
in dense blocks where statements are not separated by blank lines.
Single-letter locals should be eliminated regardless of body length.

### Concrete examples

**Project lookup, three call sites, one symbol:**

```go
// service/task.go:64
func (s *TaskService) defaultProjectID(ctx context.Context) (uuid.UUID, error) {
    p, err := s.projectRepo.GetByID(ctx, domain.DefaultProjectUUID)
    if err != nil {
        return uuid.Nil, fmt.Errorf("looking up default project: %w", err)
    }
    return p.ID, nil
}
```

Two distinct problems compound here:

1. **`p` is visually low-weight.** A single letter is the smallest
   possible token; the eye skips it on first scan. Reading
   `return p.ID` the reader has to mentally substitute "project" to
   confirm the function returns what its name promised. `project.ID`
   self-documents at the read site.
2. **The block is unseparated.** The variable definition, the
   `if err != nil` guard, and the return statement are flush against
   each other with no blank lines. In dense formatting like this, a
   single-letter identifier is even easier to miss because there is
   no visual rest between the assignment and the consumer. Naming
   the variable `project` adds the only horizontal landmark the block
   has.

The same `p` for project appears at `:65`, `:91`, and `:2103` —
three different methods, three opportunities to ask "is this project
or player?" (a `PlayerService` exists, also reachable from
`TaskService`). The shadowing is not a hypothetical: across the file,
`p` is used as project, player, parent, and pointer-formal in
helpers — four meanings for one letter.

**`t` for task across 17 ranges in `service/task.go` alone:**

```
service/task.go:361  for _, t := range tasks {
service/task.go:393  for _, t := range tasks {
service/task.go:437  for _, t := range tasks {
service/task.go:474  for _, t := range tasks {
service/task.go:503  for _, t := range tasks {
service/task.go:705  for _, t := range all {
service/task.go:774  for _, t := range descendants {
service/task.go:1431 for _, t := range tasks {
...
```

Several of these loop bodies are 30+ lines long. By the bottom of the
loop the reader has lost which list `t` came from. `task` (or
`descendant`, `actionable`, `candidate`) costs three keystrokes and
documents the role.

**Cross-file collisions:** `t` is `*domain.Task` in `service/`, but
`*treeNode` in `internal/tui/tree.go:39`, and `time.Time` in some
date-handling helpers. `n` is `*treeNode` (`tree.go:400`) and node
count elsewhere. `b` is "block" (`mcp/tools.go:666`), "bundle"
(`service/task.go`), and bytes in some renderer code. The cost is not
in any one site — it is the constant context-switch when reading
across the layers.

**Receiver names mostly land well:** `s *TaskService`, `r *Renderer`,
`a *App` — each consistent within its package and short enough not to
distract. Keep these. The problem is local variables, not receivers.

### Proposed convention

1. **No single-letter locals, regardless of scope.** `task`,
   `project`, `player`, `parent`, `child`, `node`, `bundle`, `block`,
   `descendant` — all short enough to type, none ambiguous, all
   visually distinct on a scan. The Go community's "short scope =
   short name" idiom is a defense for terseness, not a requirement;
   it is overridden here because (a) this codebase has many
   overlapping single-letter conventions across packages, and (b)
   most blocks are not visually separated, so the smallest tokens
   are the easiest to lose.
2. **Receivers stay short.** `s *TaskService`, `r *Renderer`,
   `a *App` — consistent within their package, harmless. The
   convention applies to local variables and range vars, not
   receivers.
3. **Two-element pairs may stay short only when symmetric.**
   `parent, child`, `from, to`, `lhs, rhs`. Naming both halves with
   single letters would be even worse than naming both with words;
   never write `for _, p := range parents` and `for _, c := range
   children` in the same function.
4. **Errors in batched lookups gain a noun.** `blockingErr`,
   `scoreErr`, `tagErr` instead of three sequential `err` shadows
   (see `service/task.go:325–339`). The current style is correct Go
   but the wrapping boilerplate (`loading X counts: %w` repeated four
   times) is the artifact of needing to say which `err` failed at
   the call site — named errors collapse the boilerplate and
   document the failure mode at the variable.
5. **Add a blank line between the assignment-with-error, the guard,
   and the consumer.** The dense pattern in `defaultProjectID` above
   is repeated throughout the codebase. Inserting one blank line
   between the `:=` and the `if err != nil`, and another between the
   guard's closing brace and the next statement, costs nothing and
   makes the named identifier the visual landmark the eye lands on.
   Without it, even `project` instead of `p` partially regresses.
6. **Helpers named for what they answer, not what they do.** Mostly
   already good (`filterUsesTags`, `descendantTagsLookup`,
   `uuidPtrEqual`). One outlier: `stampEffectiveWeights`
   (`service/task.go:279`) — "stamp" is a side-effect verb that
   obscures the contract; `populateEffectiveWeights` or
   `attachEffectiveWeights` would be clearer. Also `applyValidatedUpdate`
   (`:1543`) — "validated" is left over from the call site, not
   informative at the function. `commitTaskFields` or `persistUpdate`
   would say what it does.
7. **DTO names should encode their layer.** `taskJSON`, `taskResponse`,
   `treeNodeJSON` look like three coordinate types but are not. If
   they remain separate, name them by the path they serve:
   `cliTaskJSON`, `mcpTaskJSON`, `cliTreeNodeJSON`. If they unify
   (recommended; see Readability §3), one canonical name suffices.

### Worth a one-time grep-and-rename pass

`service/task.go` is the highest-leverage file: 17 `for _, t :=` sites,
three `p, err :=` patterns, and a handful of `c`/`n`/`d`/`b` locals
spread across the helpers. A single PR that renames `t → task`,
`p → project` (or `player`/`parent` per call site), `n → node`,
`c → child`, `d → descendant`, `b → block`/`bundle` across that file —
and inserts the blank-line breaks called for in convention #5 — would
test the convention against real call sites before rolling it out
further. Keep the rename scoped to one file per PR; the diff stays
reviewable and any pushback on the convention surfaces before it
spreads.

## Performance

### 1. Fan-out scoring re-fetches per project

`buildEffectiveWeights` (`service/task.go:463`) and `buildProjectWeights`
(`:432`) walk projects to compute weights; with the multi-bundle
plumbing these become per-bundle calls. Today there is one bundle so
it is fine. The moment a second bundle ships, the scoring path needs
explicit batching tests or it will be O(projects × tasks). Worth a
benchmark fixture *now* on a synthetic 1k-task / 10-project workspace
so the regression has a tripwire.

### 2. `Next` does sequential blocked-by lookups

`service/task.go:393–404` walks scored tasks, calls
`CountBlockedByTasks` for each until one is unblocked. On a workspace
with many actionable-but-blocked tasks at the top of the
urgency-sorted list, this is O(blocked-prefix) round-trips.
`listInBundle` already loaded `blockedByCounts` for the whole list at
`:329` — pass that in instead of re-querying.

### 3. `tusk task tree` rebuilds the full task list to render a subtree

`internal/tui/tree.go:32` (`buildTree`) takes a flat list and
reconstructs hierarchy in memory. For a 1039-task project (the v0.13
migration size) this is fine; for 100k it would dominate. SQLite
recursive CTEs would cap the read by traversal depth. Not urgent —
flag it as the next scaling cliff.

### 4. JSON output paths re-marshal trees recursively

`toTreeNodeJSON` (`internal/tui/tree.go:92`) recurses synchronously;
the encoder then serializes again. For deep hierarchies a streaming
encoder (`json.Encoder.Encode` per child) would halve allocations.
Microoptimization — only matters once the renderer becomes a
bottleneck.

## Long-term maintenance

### 1. Adopt the traceability matrix as repo infrastructure, not a planning artifact

The v0.13 retro recommends matrices live "alongside the spec" — make
that mechanical. A `docs/specs/<feature>.md` with a closing matrix
table, plus a `make traceability` target that grep-scans test files
for matrix-row IDs and reports unmatched rows. Without tooling, the
matrix decays into "the planner promised to maintain it." With
tooling, drift fails CI.

Highest leverage of anything in this list — the only structural fix to
the class of bug v0.13 hit.

### 2. Atomic file writes everywhere user-facing output lands

Bug 2's `> ROADMAP.md` truncation generalizes. Anywhere the codebase
writes to a user file (`tusk export`, `tusk config init`, `make
roadmap`), use `tempfile + rename` and never the shell-redirect
pattern. Add a contributor-doc rule: shell redirect to a user file is
forbidden for `tusk` outputs. The retrospective's "destructive-action
defensive pattern" category in `phase-planning-rules` is right; pair
it with a one-line repo grep that catches `> ROADMAP\|> tusk\.toml\|>
.*\.db` in Makefiles.

### 3. Test-fixture-as-prerequisite is missing for self-hosting

Phase 6's success path "could not be exercised at phase time" because
`tusk-roadmap` did not exist. The fix in the retro — phase fixtures
that create the prerequisite — should be a testing convention, not a
per-phase decision. A `tests/fixtures/roadmap/` with a 3-task
`tusk-roadmap` workspace, used by `make roadmap`'s test, would have
caught Bug 2 without the user being the integration test.

### 4. Workflow status drift between `domain` and migration SQL

The default workflow `pending ↔ active, active → completed,
{pending,active} → deleted, completed → pending` lives in CLAUDE.md,
in `migrations/003_workflows.up.sql`, in `domain/workflow.go`, and
(probably) in tests. Three sources of truth for one state machine.
Pick one (the migration SQL is most defensible since it is what the DB
enforces) and generate or assert the others from it. The
"phase-docs-as-authoritative" trap from the retrospective applied to
runtime config.

### 5. CLI command help is ~50% of `commands.go` line count and is not tested

The 380-line help string in `buildTaskCmd` and similar in
`buildPlayerCmd` describe behaviors (tag syntax, file expansion, UDA
semantics) that the parser implements separately. When the parser
changes, help drifts. A golden-test that runs `tusk task --help` and
diffs against a checked-in transcript would catch drift; better,
generate the help from the same syntax descriptors the parser uses.

### 6. Tech debt is unusually low (1 TODO across 279 files)

The flip side: there is no marked inventory of *known* compromises.
The "deferred to user-driven validation" gap from the retrospective
never got a TODO marker — it lived in the planner's head. Worth
introducing a lightweight `// DEFERRED(<phase>):` convention for
explicit deferred-validation gates so the next planner can grep for
them.

## Top picks for v0.14

Ordered by leverage. The first three pay back across every subsequent
phase; the rest are defense in depth.

1. **Traceability matrix as tooling.** Catches the largest class of
   latent defect (anything in the spec that did not make it into a
   test) and costs ~one make target.
2. **Positional-arg disambiguation helper.** Closes Bug 1's whole
   class in one place; today's silent reinterpretation surface spans
   ~10 commands.
3. **Split `TaskService` along the seams the tests already drew.**
   Unblocks every other readability and architecture point — the file
   is already the bottleneck for parallel work.
4. **Naming pass on `service/task.go`.** Try the convention on the
   highest-traffic file before rolling it out further. Reviewable
   single-PR diff.
5. **Decide on the multi-bundle story.** Either commit to fan-out with
   tests, or delete the resolver indirection. Carrying it as
   decoration costs every future contributor.
6. **Atomic-write rule + grep guard.** Prevents the next `> ROADMAP.md`
   class incident; one-line CI check.

The bugs in v0.13 were not interesting in themselves. The pattern
under them — **artifacts drift because no single one is canonical** —
shows up at every level of this codebase: phase docs vs. design spec,
help text vs. parser, three task DTOs, three sources for the default
workflow. The work above is mostly: pick the canonical artifact, drop
the others, automate the check.
