## Conventions established (Plans 1b–7.c.4)

- **Branching:** stacked PRs off `v1`. Each plan = `feat/plan-N` branched from current v1 tip. PR titled `feat(v1): plan N — <topic>` with conventional commit prefix. PR base is `v1`.
- **Bundling:** ~5–6 logical bundles per plan, one implementer subagent per bundle (general-purpose, sonnet). Smaller plans (like 7.c.2 / 7.c.3 / 7.c.4) ship as one bundle. Spec compliance verified informally with `make test` + spot-checks rather than dispatching separate reviewer subagents.
- **No pauses between bundles** — user reviews in the PR.
- **Docs style:** specs and plans avoid full function bodies. Type sketches, TOML examples, SQL DDL, JSON envelopes are fine. Tests in plan docs are shown in full (they're the precise behavioral spec); production code is described as behavior + signature + key invariants.
- **Style rules:** linter-enforced via lefthook pre-commit. Minimum 2-character identifiers, blank lines around err guards, named errors on shadow. Never `--no-verify`.
- **Stale LSP diagnostics:** `<new-diagnostics>` blocks frequently fire after subagent commits land — they show errors that aren't real. Verify with `go test ./... && make lint` before reacting.
- **PR titles:** conventional commit prefix (`feat(v1):`, `chore:`, etc.). The pr-title workflow enforces this.
- **Plan/spec doc commits:** spec lands as its own `docs(spec):` commit; plan as `docs(plan):` — both before any implementation commits on the branch.
- **Spec amendments:** when implementation reveals the spec was wrong (7.c.3 status-enum case — see lessons below), amend the spec (and plan) doc in a follow-up `docs(spec): amend` commit on the same feature branch. Do not silently let code drift from spec.
- **Cleanup after merge:** `git checkout v1 && git pull && git branch -D feat/plan-N` is the cleanup ritual. Remote branches are auto-deleted on merge.
- **No Claude attribution** in commits or PRs (no Co-Authored-By, no "Generated with Claude Code" footers).

## Lessons from 7.c.1 / 7.c.2 / 7.c.3 / 7.c.4 worth keeping in mind

1. **Architectural shifts during brainstorm are the norm, AND so are mid-implementation corrections.** 7.c.1 dropped Layer 1 overrides. 7.c.3 dropped the `project` node type. 7.c.4 dropped the master spec's structured `decision` schema. **7.c.3's brainstorm landed an enum-based `status` design that turned out to be structurally illegal** (the behavior engine reserves the workflow's status-property exclusively via `internal/behavior/engine.go:125 detectCollisions`); the implementer caught it during the smoke test, the spec/plan were amended in follow-up `docs(spec): amend` / `docs(plan): amend` commits, and a residual was added documenting the constraint as a brainstorm-time false premise. **Cross-check `ReservedKeys()` semantics in advance when brainstorming designs around behavior-pack-governed properties.**
2. **`ResolveRefs` fallback path (Bundle 4 of 7.c.1)** — when reindex's `ResolveEdges` (Plan 2) moves ref values from `Properties` to `Edges` before `ResolveRefs` runs, the resolver falls back to reading from `Edges`. Service.Create avoids this by ordering `ResolveRefs` before `ResolveEdges`. Two code paths with different value-source assumptions — code-path-dependent smell, may benefit from re-ordering reindex's pipeline rather than carrying the fallback. Worth a follow-up cleanup whenever someone is touching reindex.
3. **Plan docs containing CLI smoke tests need verified flag shapes.** Lesson surfaced in 7.c.2; 7.c.3 and 7.c.4 plan docs both included an explicit "verify flag shapes against the actual CLI source before locking the smoke test" note in the plan, and the implementers did so. Continue the pattern. Current verified flag shapes as of v1 tip `d8dde4c`: `node create --type --title --path --prop`; `node modify <id> --prop --unset`; `edge add --type --source --target`; `edge list --from --to --type`; `pack add <name|url> [--force]`; `reindex` (no flags).
4. **Plan-spec drift caught at implementation time.** Plan 7.b Bundle 1 caught `title` (a reserved property name) in test fixtures. 7.c.3 caught the status-enum constraint. 7.c.4 had no surprises — the implementer reported DONE on first try. Implementer subagents should be encouraged to flag (not silently change) plan/spec disagreements; they're often real bugs.
5. **MCP structured warnings via text-parsing remains a v1 expediency.** Plans 7 and 7.b both used stderr text-line parsing instead of a structured warning channel. 7.c.1's MCP envelope work used `errors.As(*node.RefValidationError)` for hard errors (structured) but warnings would still need promotion. Carry forward.
6. **Auto-cleanup test helpers.** `cmd/tusk/cmd_test_helpers_test.go`'s `chdir(test, dir)` registers `t.Cleanup` internally and returns nothing. Past plan docs sometimes wrote `previous := chdir(...); defer previous()` — wrong shape. Cross-check helper signatures before writing test code in plans.
7. **Wikilink-as-edge UX is gated on `[edge-types.references]` being declared** (7.c.4 lesson). The vault pack carries this declaration; without the vault pack, body wikilinks render as plain text only. A future plan that wants wiki UX without note/meeting/decision node types would either (a) auto-include `[edge-types.references]` in any pack that uses wikilink-edges, or (b) split it into a dedicated minimal "wiki-core" pack. Captured as 7.c.4 §7 residual #1.
8. **Pack platform is mature — three packs shipped without engine touch.** Tags, kanban, and vault all landed with pure data + a single end-to-end smoke test. The pack platform pattern (alias map → file fetch → atomic merge → manifest-load validation) has now been exercised against three real packs and is stable. Future packs (`org`, `people`, etc.) should follow the same shape.
