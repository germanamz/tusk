## What Was Built

v0.8 makes tusk embeddable as a Go library. Core packages were moved out of `internal/` to top-level, making them importable by external programs. A high-level `Client` type in the root package wires up config, database, migrations, and all services behind a single `NewClient(Config)` call.

### Package Restructure

All core packages moved from `internal/` to top-level:

| From | To | Rationale |
|------|-----|-----------|
| `internal/domain` | `domain` | Core types needed by all consumers |
| `internal/config` | `config` | Config types needed by Client |
| `internal/repository` | `repository` | Interface definitions for custom backends |
| `internal/filter` | `filter` | Filter parsing for programmatic queries |
| `internal/service` | `service` | Business logic — the primary API surface |
| `internal/sqlite` | `sqlite` | Default storage implementation |
| `internal/inmem` | `inmem` | Config-backed in-memory repos |

Packages that remain in `internal/`: `internal/tui` (CLI rendering) and `internal/mcp` (MCP server wiring).

### High-level Client

| Component | Package | Status | Notes |
|-----------|---------|--------|-------|
| `Config` struct | root (`tusk`) | Done | `DBPath`, `Workflows`, `Projects`, `Urgency` — reuses `config` package types |
| `Client` struct | root (`tusk`) | Done | 6 public service fields, private `store` |
| `NewClient(Config)` | root (`tusk`) | Done | Validate → defaults → mkdir → SQLite → repos → services |
| `Close()` | root (`tusk`) | Done | Releases DB connection |
| `config.Validate()` | `config` | Done | Exported for use by Client (was unexported `validate()`) |
| Default config injection | root (`tusk`) | Done | Builtin kanban workflow, default project, default urgency weights |
| Integration tests | root (`tusk`) | Done | 4 tests: create+get, defaults, empty path, close |

### Consumer Usage

```go
client, err := tusk.NewClient(tusk.Config{
    DBPath: "/tmp/my-tasks.db",
})
defer client.Close()

task := &domain.Task{Title: "Build the thing"}
client.Tasks.Create(ctx, task)
```

For full control, consumers can import building-block packages directly:

```go
import (
    "github.com/germanamz/tusk/domain"
    "github.com/germanamz/tusk/repository"
    "github.com/germanamz/tusk/service"
    "github.com/germanamz/tusk/sqlite"
)
```

## Key Features in Detail

### NewClient Wiring

`NewClient` replicates the DI wiring from `cmd/tusk/main.go` without Viper, CLI flags, or TUI/MCP concerns:

1. Validates `DBPath` is non-empty
2. Injects builtin defaults for zero-valued config (kanban workflow, default project, default urgency weights)
3. Validates config cross-references via `config.Validate()` (projects must reference existing workflows)
4. Ensures parent directory exists
5. Opens SQLite with WAL mode, auto-migrates
6. Creates all repos (5 SQLite + 2 inmem) and 6 services
7. Returns `Client` with services as public fields

### Default Config Behavior

When config fields are zero-valued:
- `DBPath` empty → error (required)
- `Workflows` empty → builtin kanban (pending, active, completed, deleted)
- `Projects` empty → builtin default project with kanban workflow
- `Urgency` zero-valued → default weights matching `config/default.toml`

This mirrors CLI behavior when no config file exists.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Config types | Reuse `config.WorkflowConfig`, `config.ProjectConfig`, `config.UrgencyConfig` | No duplication; types are already public and stable |
| Store visibility | Private field, exposed only via `Close()` | Consumers interact through services; raw DB is an implementation detail |
| Migrations | Always run automatically | Matches CLI behavior; consumers who want control use building-block packages |
| Default injection | Hardcoded constants matching `default.toml` | Client bypasses Viper; avoids file I/O dependency |
| Config validation | Export `config.Validate()` | Single source of truth for cross-reference checks |
| Service field names | Short names (`Tasks`, `Tags`) | `Client` type provides sufficient context |

### Known Limitations

- **No pagination** — `tusk list` and `tusk available` return all matching tasks
- **UDA values are untyped** — all values stored as strings; typed UDA validation deferred
- **Default values duplicated** — builtin workflow/project/urgency defaults are hardcoded in `client.go` separately from `config/default.toml`; a future `config.DefaultWorkflows()` helper could unify them
- **No config file loading in Client** — by design; consumers who want Viper-based config use `config.Load()` and map to `tusk.Config` themselves

## Next: v0.9 — Configuration Management

1. **Config CLI** — `tusk config show/get/set/edit/validate/init` for inspecting and modifying configuration
2. **Workflow CRUD** — `tusk workflow create/modify/delete` with inline key:value syntax
3. **Project CRUD** — `tusk project create/modify/delete` with per-project database paths
4. **Local config discovery** — walk-up config resolution (CWD → global → ancestor)
