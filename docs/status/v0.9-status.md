## What Was Built

v0.9 turns tusk's TOML configuration from a read-only file into a managed surface. Humans and agents can now inspect, mutate, and validate configuration through the CLI and MCP without hand-editing `tusk.toml`. Workflows and projects gain full CRUD with an inline key=value syntax. The config loader gains local discovery (walk-up `tusk.toml`), an explicit `--config` flag, and a hot-reload path so MCP mutations take effect without restarting the server.

Two other concerns landed alongside the headline feature: workflow statuses moved to a role-based representation (no more hardcoded status strings), and the filter/inline-syntax lexer migrated from `:` to `=` as the field separator, freeing `:` for value modifiers like ordered sequences. The workspace model was also simplified — the short-lived per-project database path was removed before release, collapsing back to a single-database workspace.

## Key Features in Detail

### Config Discovery Precedence

`config.ResolveConfigFile` is the single source of truth for "which file should we read/write?":

1. **Explicit file** — `--config` flag or `TUSK_CONFIG` env var. Missing file = hard error.
2. **Walk-up discovery** — start at CWD (or `--start-dir`), climb ancestors looking for `tusk.toml`. First match wins.
3. **Global config** — `$XDG_CONFIG_HOME/tusk/config.toml` (or platform equivalent). Returns `""` if absent.
4. **Defaults only** — loader falls back to embedded `default.toml`; no file is touched.

`Load` and `ConfigFilePath` share this resolver, so the CLI (`config show`, `config edit`), the programmatic `Client`, and the MCP server all see the same "active file".

### Inline Workflow / Project Syntax

CLI mutations use the same inline token stream as filters, extended with dot-path keys and `+`/`-` modifiers:

```bash
# create a workflow with role-tagged statuses and transitions
tusk workflow create kanban \
  status=pending\(initial,start\) \
  status=active \
  status=done\(terminal\) \
  transition=pending:active,active:done

# add a review status and a new transition without replacing the rest
tusk workflow modify kanban +status=review +transition=active:review,review:done

# project with per-project urgency overrides and an auto-complete trigger
tusk project create backend \
  workflow=kanban \
  urgency.priority_weight=4.0 \
  urgency.due_weight=2.5 \
  auto-complete.trigger=subtasks \
  auto-complete.target=parent

# bump priority weight by +0.5, clear due weight
tusk project modify backend +urgency.priority_weight=0.5 -urgency.due_weight
```

The parsers live in `internal/tui/workflow_parse.go` and `internal/tui/project_parse.go`; both build on the shared `syntax` lexer so modifiers and value parsing stay consistent with filters.

### MCP Hot Reload

The MCP server cannot restart itself between tool calls, so config mutations need to take effect in-process:

1. `tusk_config_set` / `tusk_workflow_*` / `tusk_project_*` acquire the server's `configMu` mutex.
2. The handler mutates the TOML file via the `config` package helpers and re-validates.
3. `reloadConfigLocked` re-reads the file, then calls `SetWorkflows`, `SetProjects`, and `SetDefaults` on the in-memory repos and urgency engine.
4. Subsequent tool calls observe the new config without restarting the MCP transport.

Workflow and project MCP mutations serialize under the same mutex as `tusk_config_set`, so there is no window where a partial update is visible.

### Storage Key Guard

`tusk_config_set` refuses to mutate anything under `storage.*`. The rationale: the active database path is pinned when the server starts, and silently changing it mid-session would leave handles pointing at a file nobody can see. Humans who really need to change storage keys edit the TOML directly and restart.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Single-store workspace | Removed `ProjectConfig.db_path` | Complexity of cross-store relations was not worth the ergonomic win; revisit post-v1 if multi-tenant demand appears |
| Config discovery order | Explicit → walk-up → global → defaults | Matches how developers expect project-scoped tooling (git, eslint) to behave |
| `:` → `=` separator | Migrated all inline syntax | Frees `:` for value modifiers (ordered sequences, transitions) and disambiguates from filter values containing colons |
| Role-based workflow statuses | `StatusConfig` with `initial`, `start`, `done`, `delete`, `terminal` flags | Removes hardcoded `"pending"` / `"active"` strings from the service layer; custom workflows can now rename every status |
| Inline modifiers as token bytes | `Token.Modifier byte` + `ModifierSet` registry | Keeps the lexer single-pass and makes new modifiers (e.g. `~`, `!`) a registry change, not a grammar change |
| MCP hot reload | Re-read TOML + swap repos under mutex | Alternative would be restarting the MCP transport on every mutation — unacceptable for agent workflows |
| `storage.*` read-only via MCP | Explicit guard in `tusk_config_set` | Swapping the DB path mid-session is an operator action, not an in-band mutation |
| Config write atomicity | Write to temp file, rename | Prevents corrupt TOML if the process dies mid-mutation |
| Workflow / project delete guards | Block when referenced, `force` bypass | Matches the rest of tusk's "safe by default, explicit override" posture |
| `--config` stripped before Cobra | Parse in `main.go` prelude | Lets the flag work in front of any subcommand without every command re-declaring it |

### Known Limitations

- **Single workspace database** — all projects share one SQLite file. The per-project `db_path` field that was briefly in `ProjectConfig` was removed before release.
- **No undo for config mutations** — `config set` and the workflow/project CRUD commands are destructive; recovery is "edit the TOML by hand" or restore from source control.
- **`storage.*` is not mutable via MCP** — operators must edit the file and restart the server.
- **Hot reload is in-process only** — external consumers of the Go library must opt in by calling the `Set*` hooks themselves; the embedded `Client` does not watch the file.
- **No pagination** — unchanged from v0.8.

## Next: v0.10 — Trailing Window Notes

The v0.10 milestone adds a bounded, append-only note buffer per task so that humans and agents can capture ambient context (what they tried, what they observed) without growing the annotations list unboundedly. Expected scope:

1. **Note buffer storage** — fixed-size ring per task, SQLite-backed.
2. **CLI + MCP surface** — `tusk note add / list / clear` and matching MCP tools.
3. **Urgency engine hook** — optionally factor recent note activity into urgency scoring.
4. **Retention policy** — config-driven window size; eviction on overflow.
