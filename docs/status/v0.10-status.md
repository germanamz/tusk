# Tusk v0.10 — Implementation Status

> Last updated: 2026-04-15
> Milestone: v0.10 Datastore-Backed Projects & Workflows — **Complete**

For the full design spec, see [PRODUCT.md](../../PRODUCT.md). For v0.9 recap, see [v0.9-status.md](v0.9-status.md).

---

## What Was Built

v0.10 moves projects and workflows out of the TOML config file and into the workspace database. Tasks already lived in SQLite; projects and workflows are now workspace data too, with optimistic locking, referential integrity, and the same service/repository layering that backs every other mutable entity.

The user-visible surface is deliberately unchanged. `tusk project create/modify/delete/list` and `tusk workflow create/modify/delete/list` (and their MCP counterparts) behave exactly as in v0.9 — the CLI arguments, inline syntax, error messages, and output shapes are preserved. What moved is the write target: mutations now flow through `ProjectService` / `WorkflowService` to SQLite repositories, not through `config.CreateProject` / `config.CreateWorkflow` to TOML file writes. `config show` still renders `[projects.*]` and `[workflows.*]` sections for continuity, but the values are hydrated from the database at display time and marked read-only in the header.

The config file now holds global settings only: `[storage]`, `[urgency]`, `[tui]`, `[mcp]`. A legacy-section hard error in `config.Load` catches files still carrying `[projects.*]` or `[workflows.*]` and points users at the new `tusk project` / `tusk workflow` commands.

## Key Features in Detail

### Projects and Workflows as Workspace Data

Before v0.10, a project or workflow existed only because it was read out of `config.Config.Projects` / `.Workflows` after every `config.Load`. Mutations rewrote the TOML file; the MCP server held a `configMu` mutex to serialize writes because TOML files are not transactional. In-memory repository implementations (`inmem.ProjectRepository`, `inmem.WorkflowRepository`) existed solely to expose the TOML-derived maps behind the repository interface.

In v0.10 projects and workflows are first-class database entities:

- Each carries an `id` UUID, a human-readable `name`, a `version` for optimistic locking, and `created_at` / `updated_at` timestamps — identical to `Task`.
- `Project.settings` is a JSON blob holding `auto_complete`, `auto_revert`, and `urgency` overrides. JSON was chosen over dedicated columns because per-project settings are read once per service call and written rarely; promotion to columns is available as a follow-up if profiling shows the decode is hot.
- `Workflow.statuses` and `Workflow.transitions` are JSON blobs keyed/ordered the same way they were in the TOML schema, so the role-based validation logic from v0.9 ports over verbatim.
- `tasks.project_id` is now a real foreign key to `projects(id)` with `ON DELETE RESTRICT`. The service-level "reject delete if tasks reference it" guard still runs first, but the FK provides a database-level safety net.
- Workflows are referenced via `projects.workflow_id` with `ON DELETE RESTRICT`. Deleting a workflow that any project points at is blocked at both the service layer (`CountByWorkflow`) and the database.

### Service Layer Ownership

`ProjectService` and `WorkflowService` are now thin authoritative layers over their SQLite repositories:

- `Create` validates input, builds the domain entity, and calls `repo.Create`.
- `Modify` fetches the current row (to read `version`), applies the requested changes, and calls `repo.Update(version)`. A version mismatch bubbles up as `domain.ErrConflict` — identical to task mutations.
- `Delete` runs the guard chain (referenced-rows check, built-in protection, `force` override) and then calls `repo.Delete(version)`.

Role-schema validation (exactly one `initial`, one `start`, ≥1 `terminal`, one `done`, one `delete`) moved out of `config.Validate` into `WorkflowService`. That was the last piece of business logic living in the config package; after v0.10 `config` is a pure loader again.

### Config File Trim and Legacy Guard

The config file now holds **globals only**:

```toml
[storage]
backend = "sqlite"
path    = "~/.local/share/tusk/tusk.db"

[urgency]
priority_weight    = 6.0
# …

[tui]
date_format = "2006-01-02"
# …

[mcp]
disabled_tool_groups = []
# …
```

Running `tusk` against a v0.9-era file that still has `[projects.foo]` or `[workflows.bar]` fails at `config.Load` with:

```
Error: loading config: config file /path/to/tusk.toml contains [projects.*] sections — projects and workflows are now managed in the database. Remove the section(s) from the file and recreate the equivalent entries via `tusk project` / `tusk workflow`
```

The guard applies to explicit `--config` paths, `TUSK_CONFIG` env vars, walk-up hits, and the global `~/.config/tusk/config.toml`. Only the embedded-defaults-only path (no file at all) is exempt, since the embedded default is already trimmed.

### `config show` Still Renders Projects and Workflows

User continuity was a hard requirement: a user who runs `tusk config show` should see the complete picture of their workspace, not be forced to mentally join three commands. v0.10 keeps the rendered sections but sources them from the database:

```
# active: /Users/you/.config/tusk/config.toml
[storage]
…
[mcp]
disabled_resource_groups = []
disabled_resources = []

# workflows (from database — use `tusk workflow` to modify)

[workflows.kanban.statuses.pending]
roles = ["initial"]

[workflows.kanban.statuses.active]
roles = ["start", "highlight"]
# …

[[workflows.kanban.transitions]]
from = "pending"
to = "active"
# …

# projects (from database — use `tusk project` to modify)

[projects.default]
workflow = "kanban"
```

JSON output (`--output json`) emits a single flat object with `storage`, `urgency`, `tui`, `mcp`, `projects`, and `workflows` keys at the top level. The `projects` and `workflows` maps are populated by converting `*domain.Project` / `*domain.Workflow` through internal view types — `config show` has no remaining dependency on the deleted `config.ProjectConfig` / `config.WorkflowConfig` structs.

Reading and writing are asymmetric on purpose: `config get projects.backend.urgency.blocking_weight` still resolves (routed through `projectSvc.GetByName`), but `config set projects.backend.workflow kanban` now fails with a pointer to `tusk project modify`. The same asymmetry applies to the MCP `tusk_config_set` tool.

### CLI and MCP Unchanged Above the Service Boundary

`tusk project` and `tusk workflow` subcommands — and their MCP counterparts — keep their v0.9 surface verbatim. Inline syntax (`workflow=kanban`, `urgency.blocking-weight=15`, `+urgency.blocking-weight=2`, `auto-complete.trigger=completed`) produces the same AST. Error messages and output formats are preserved. What changed is the target of the write: `service.ProjectService.Modify(ctx, …)` → `sqlite.ProjectRepo.Update(ctx, …)` instead of `config.ModifyProject(…)` → TOML write.

Numeric urgency delta resolution is the one subtle place worth flagging: `+urgency.blocking-weight=2` means "add 2 to the current effective weight". In v0.9 the current weight came from the TOML file; in v0.10 it comes from the effective global weight (still in config) plus any prior override stored in `projects.settings`. The resolved absolute value is what lands in the JSON settings blob, so the next read picks it up directly without re-deriving from a delta.

### MCP `configMu` Gone

The v0.9 MCP server held a process-wide `configMu` mutex so concurrent `tusk_config_set` / `tusk_project_*` / `tusk_workflow_*` calls couldn't race each other's TOML writes. With DB-backed mutations and optimistic locking, the mutex is redundant: SQLite serializes writes at the engine level, and `version`-checked updates surface conflicts as `ErrConflict` for the caller to retry.

Removing the mutex means two agents can issue `tusk_project_modify` for different projects in parallel without one blocking the other. It also means the `ConfigReloadHook` plumbing — which existed to swap in-memory repos after a TOML mutation — goes away entirely, simplifying the MCP server constructor and its test harness.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Project settings column shape | JSON blob | Read-once-per-call access pattern; promotion to typed columns deferred until profiling justifies it |
| Workflow statuses + transitions storage | JSON blobs on the workflow row | Avoids a second table just for status rows; keeps role validation simple |
| Task → project FK | Real FK with `ON DELETE RESTRICT` | Database-level backup for the existing service-layer guard; defense in depth |
| Workflow → project reference | FK on `projects.workflow_id` with `ON DELETE RESTRICT` | Mirrors the task→project guard at the DB layer |
| Default project/workflow seeding | Inserted by migrations 003/004/006 | Removes the need for a startup-time sync path; fresh DBs are usable immediately |
| `_default` → `default` rename | One-shot migration 006 | The service layer expects a single name; sync-time rewriting was fragile |
| `SyncConfigToDB` | Deleted entirely | Redundant once migrations seed the rows; kept briefly as a bootstrap path, removed at the end of v0.10 |
| `inmem` package | Deleted | Existed only because TOML was the source of truth; no longer has a reason to exist |
| Legacy `[projects.*]` / `[workflows.*]` | Hard error at `config.Load` | Silent ignore would strand user data; a loud pointer to the new commands is the right UX |
| Role constants location | `domain.StatusRole` values, not `config.Role*` | Roles are domain concepts; removing from `config` matches the "config is a loader" cleanup |
| MCP `configMu` | Deleted | DB-level optimistic locking replaces it; allows concurrent cross-entity writes |
| `config show` DB rendering | Hand-rolled view types, not aliases of deleted `config.*` types | Decouples display from the config schema trim and prevents latent compile breaks |
| `tusk.Config.Workflows` / `.Projects` | Removed from the public library API | No programmatic consumer should be seeding workflows via the client; they call `client.Projects.Create` / `client.Workflows.Create` directly |

### Known Limitations

- **`storage.*` still read-only via MCP** — unchanged from v0.9; operators edit the TOML and restart.
- **No undo for project/workflow mutations** — destructive operations are guarded but not reversible; recovery is `git`-style (backup, `tusk project create` replay).
- **Single workspace database** — unchanged from v0.9.
- **Legacy config files are a hard error, not an auto-migration** — users with `[projects.*]` / `[workflows.*]` in their TOML must remove the sections and replay via `tusk project create` / `tusk workflow create`. A dedicated `tusk config migrate-legacy` command was considered and deferred; the audience for this milestone is pre-1.0 and we preferred the loud-failure signal over silent data migration.

## Next: v0.11 — CLI Command Grouping

v0.11 reorganizes the CLI into subcommand groups: every task-scoped command moves under `tusk task …`, every project-scoped command under `tusk project …`, and so on. Verbs, flags, inline syntax, and output are unchanged — only the invocation path moves. Pre-release, so no backward-compat aliases are kept. Expected scope:

1. **`tusk task` subcommand group** — `task add` → `task create`, `task info` → `task get`, etc.
2. **`tusk project` / `tusk workflow` / `tusk tag` / `tusk note` groups** — flatten command trees that currently split across multiple verbs.
3. **Help text, MCP tool names, and docs refresh** — align with the new grouping.
4. **e2e test migration** — every scenario updates to the new paths in one sweep.
