## What Was Built

v0.3 adds the MCP (Model Context Protocol) server for AI agent integration. The server exposes all task management capabilities as MCP tools and resources over stdio transport, enabling AI agents in IDEs and other MCP clients to manage tasks programmatically.

## Key Features in Detail

### MCP Tools

Every tool maps 1:1 to a service method. Tools return JSON with full entity data including `version` for optimistic locking.

| MCP Tool | Service Method | Description |
|----------|---------------|-------------|
| `tusk_task_create` | TaskService.Create | Create task with title, priority, project, parent, tags, due, wait_until |
| `tusk_task_get` | TaskService.GetByShortID | Rich response: task + tags + relations + annotations |
| `tusk_task_list` | TaskService.List | Structured filters: status, priority range, project, tags, due range, parent, root |
| `tusk_task_modify` | TaskService.Update | Partial update with add_tags/remove_tags, version required |
| `tusk_task_start` | TaskService.Start | Transition to active, returns updated task with tags |
| `tusk_task_done` | TaskService.Complete | Transition to completed, returns updated task with tags |
| `tusk_task_delete` | TaskService.Delete | Soft-delete (→ deleted), returns updated task with tags |
| `tusk_task_annotate` | TaskService.Annotate | Add timestamped note |
| `tusk_task_tree` | List + GetDescendants | Nested JSON tree with `include_deleted` boolean flag |
| `tusk_relation_add` | RelationService.Add | Create relation with enum type validation |
| `tusk_relation_remove` | RelationService.Remove | Remove relation |
| `tusk_project_list` | ProjectService.List | List all projects with settings |
| `tusk_project_create` | ProjectService.Create | Create project with name and description |

### MCP Resources

Read-only views of state accessible via `resources/read`:

| Resource URI | Description |
|-------------|-------------|
| `tusk://tasks/{short_id}` | Full task detail (same format as `tusk_task_get`) |
| `tusk://projects/{name}` | Project with settings |
| `tusk://projects/{name}/workflow` | Workflow statuses and allowed transitions |

### Error Handling

Domain errors map to MCP tool-result errors (`isError: true`), not transport failures. This lets agents read and react to errors programmatically.

| Domain Error | MCP Error Message |
|---|---|
| `ErrNotFound` | `not found: <context>` |
| `ErrConflict` | `version conflict: task was modified, re-fetch and retry` |
| `ErrInvalidTransition` | `invalid status transition` |
| `ErrCyclicBlock` | `would create a dependency cycle` |
| `ErrCyclicParent` | `would create a parent-child cycle` |
| `ErrDuplicateRelation` | `relation already exists` |
| `ErrSourceNotFound` | `source task not found` |
| `ErrTargetNotFound` | `target task not found` |

### Optimistic Locking

All mutation tools (`modify`, `start`, `done`, `delete`) require a `version` parameter. All task tool responses include `version`. Agents must fetch the current version before mutating — stale versions return a version conflict error.

## Architecture

The `internal/mcp/` package follows the same pattern as `internal/tui/`:

```
Server struct (holds service dependencies)
  ├── server.go     — New(), Serve(), registerTools(), registerResources()
  ├── tools.go      — 13 tool handler methods + response types
  ├── resources.go  — 3 resource handler methods
  └── errors.go     — mapError() domain → MCP translation
```

Key design decisions:
- **Flat registration** — All tools registered in a single `registerTools()` method, matching the TUI's single-file command pattern.
- **Thin adapters** — Each handler extracts params, calls the service layer, formats the response. No business logic in the MCP layer.
- **Shared helpers** — `buildTaskGetResponse()` is used by both `handleTaskGet` and `handleTaskResource` to avoid duplication. `handleTaskTransition()` is shared by start/done/delete.
- **Structured params over DSL** — `tusk_task_list` accepts explicit filter fields (status array, priority range, etc.) rather than the TaskWarrior filter syntax. Better for agent ergonomics.

### Service Layer Change

`WorkflowService` gained a `GetTransitions()` method (delegates to `WorkflowRepository.GetTransitions`) to support the workflow resource template. The `Server` struct accepts `*service.WorkflowService` in addition to the existing four service dependencies.

`tui.App` also gained a `workflowSvc` field to pass through to the MCP server.

### Known Limitations (carried from v0.2)

- **No quoted string support in filters** — `title:"my task"` and `description:` filters blocked until the lexer supports quoted strings
- **No boolean operators** — filters are AND-only; OR only within comma-separated values
- **No pagination** — `tusk list` returns all matching tasks
- **No sorting** — tasks returned in `created_at` order (urgency sorting is v0.6)
- **No config file loading** — `config/default.toml` exists as a template but isn't read at runtime
