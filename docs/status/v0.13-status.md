## What Was Built

v0.13 makes tusk usable as the source of truth for its own roadmap. The hand-edited `ROADMAP.md` is gone; the file is now regenerated from a tusk project (`tusk-roadmap`) on every `make roadmap`. Getting there required eight initiatives — a foundational event log, task-level taxonomy, sibling ordering, subtree urgency overrides, a static progress rollup view, bidirectional data portability, the markdown renderer that powers the regenerated file, and the repo-root tusk workspace migration that lets the dogfood DB live next to the code.

Beyond the self-host story, v0.13 ships the foundational primitives the v0.14 milestone (live dashboard) and v0.15 milestone (undo, webhooks) will build on:

- **Event Log** — append-only record of every task/relation mutation, written transactionally inside the same SQLite transaction as the row write. The undo and webhook foundations both consume this log directly.
- **Task Level Taxonomy** — replaces the dropped UDA-Schema-Validation initiative. Per-project ordered list of allowed `level` values (e.g. `milestone > initiative > story > task`) with parent-child constraint enforcement and a `level=` filter.
- **Sibling Ordering** — explicit `order` column on tasks, `tusk task move` / `tusk task resequence` commands, and corresponding MCP tools, so document-position can survive a roundtrip through tusk.
- **Subtree Urgency Overrides** — per-task `urgency_overrides` map that overlays the global urgency engine for that task and every descendant. Lets a roadmap node pin priority weights without touching the workspace defaults.
- **Progress Rollup** — `domain.AggregateRollup` plus `tusk task tree --rollup`, `tusk task summary`, and `tusk_task_summary` MCP. Branch nodes annotate with `[done/total done, %]  (status: count, ...)` using v0.9 status roles.
- **Data Portability** — bidirectional JSON export/import via `tusk export` and `tusk import`. Replace and Truncate modes, dry-run, deterministic output. CSV deferred to a later milestone.
- **ROADMAP.md Migration** — markdown renderer for `tusk task tree --format markdown`, project-description column, project-scoped notes, annotation/note rendering, and a one-shot tracker that walked the existing roadmap into the tusk project.
- **Repo-Root Tusk Workspace** — `tusk.toml` and `.data/tusk.db` live at the repo root. The e2e suite was migrated to a layered `Env` / `MCPEnv` harness so config-walkup tests can run without polluting the dogfood DB.

## Key Features in Detail

### Event Log Transactional Semantics

Every service-layer mutation now opens a `WriteTx` (the existing transaction abstraction added in earlier milestones) and records exactly one event inside it before commit. The `WriteTx.Events()` accessor returns the same `EventRepository` instance bound to the transaction, so the row write and the event row land or roll back together. There is no out-of-band emission path; an event without a corresponding row write is structurally impossible.

`task_moved` is the trickiest case — re-parent + re-order is a single SQL statement (`UpdateOrderAndParent`) and emits one event with both `from`/`to` parent IDs and `from`/`to` order values. `task_resequenced` emits one event per parent (not per child) and carries the count of renumbered children plus the parent ID.

### Task Level Taxonomy and the Dropped UDA Schema Validation Initiative

The original v0.13 plan called for a generic UDA schema validator. Mid-milestone the scope was reduced to a single first-class field, `level`, because the only UDA the roadmap migration actually cared about was the level (milestone/initiative/story/task) and a generic schema layer would have been weeks of additional work for no dogfood payoff. UDA Schema Validation reappears in a future milestone; v0.13 ships only what the self-host needed.

Per-project taxonomy is an ordered list — index 0 outranks index 1, and the constraint check fires on `Update` (creating a child whose level outranks its parent's). `LevelService.Check` runs as a separate validation command (`tusk task level-check`) so tooling can ask "would this level be valid here?" without committing.

### Sibling Order Math

`order` is a float so siblings can be inserted between two existing ones without renumbering. `Move` uses midpoint math (`(prev + next) / 2`) with `(prev - 1)` / `(next + 1)` for the extremes; `Resequence` collapses a parent's children to dense integers (`1, 2, 3, …`) when the gap shrinks below a threshold. `ErrOrderGapExhausted` surfaces with the parent's short ID so the user can run `tusk task move --resequence <parent>` to recover.

The cycle check on Move uses `TaskRepository.GetDescendants` (single recursive CTE) and refuses moves that would make the subject its own ancestor.

### Urgency Override Resolution

`urgency_overrides` is a `map[string]float64` keyed by weight name (`priority_weight`, `due_weight`, …). On every urgency calc, the engine walks ancestors from the task itself upward, taking the first ancestor that has a non-empty overrides map. The chosen overrides merge over the global defaults — present keys override, absent keys fall through. This means a milestone-level pin propagates to every descendant unless an intermediate ancestor pins again.

The CLI surface uses a `urgency.` prefix (`urgency.priority_weight=2.5`) symmetric with `uda.` and `meta.`. Empty value (`urgency.priority_weight=`) clears one key. The literal `urgency.clear` token resets the whole map; the MCP equivalent is the boolean `urgency_overrides_clear`.

### `domain.AggregateRollup`

A pure function over a slice of descendants and a workflow-resolver. v0.9's status-role system (`done`, `delete`) drives the math — `delete`-role tasks are excluded from totals; `done`-role tasks count toward both `Done` and `Total`. Multi-workflow descendants merge by status name; the seed workflow's full status order pre-populates per-status counts with zeros so renderers always have stable columns. Filter-mode summaries use the same function twice — once to select blocks, once per block to roll up that block's descendants.

The math runs in Go, not SQL. The filter pipeline is already Go-side, and pushing aggregation to SQL would fork the rollup off the filter contract.

### Bidirectional JSON Portability

`tusk export` walks every entity kind through the existing services — workflows, projects, players, tags, tasks, relations, annotations, notes, events — into a `PortableWorkspace` value, then encodes deterministically (sorted map keys, stable slice ordering, ms-truncated timestamps). The default mode is fail-fast on collision; `--replace` upserts rows by ID; `--truncate` wipes the destination tables before applying the dump (requires `--replace`). `--dry-run` runs the validation pass and reports per-kind counts without writing.

Schema-version awareness: the export carries a `SchemaVersion` constant; import refuses dumps whose version exceeds the importer's. Unknown event kinds round-trip through `domain.UnknownPayload` so a v0.13 build can ingest a future-version dump without dropping events on the floor.

CSV is explicitly out of scope for v0.13 — design captured in the spec, deferred to a later milestone.

### ROADMAP.md as Generated Output

The hand-edited `ROADMAP.md` is gone. The file is now produced by `tusk task tree project=tusk-roadmap --format markdown` and the `make roadmap` target wraps that with an atomic temp→rename. CI regenerates the file on every release; if the generated output drifts from `git`, the commit is rejected.

The renderer emits an H1 from the title-cased project name, a `> ` blockquote with the project description, and a nested H2/H3/bullet structure walking the task tree. Inline tokens (`status=…`, `level=…`, `+tag`, etc.) follow the task title using the same lexer the inline-field CLI uses. Annotations and notes render as `**Annotations:**` / `**Notes:**` sub-blocks; archived notes never reach the renderer (the gathering layer queries with `IncludeArchived: false`). Project-level notes (`task_id IS NULL`) appear under the H1 description before the first task.

The renderer rejects `--rollup` and multi-project trees; an empty workspace emits no output.

### Repo-Root Workspace and the Walk-Up Harness

`tusk.toml` at the repo root makes the dogfood DB the canonical workspace for development. The e2e suite needed a way to run config-walkup tests without ever seeing this file, so v0.13 introduced a layered harness in `tests/e2e/harness.go`:

- `Env` — base CLI harness; spins up an isolated workspace inside `t.TempDir()`, builds a binary scoped to that directory, exposes `Run(...)` for CLI invocations.
- `MCPEnv` — wraps `Env` with an MCP stdio child process for MCP-flavored tests.
- Walk-up isolation — every harness env points the binary at its own `tusk.toml` so config discovery cannot reach the repo root.

`TUSK_DB` was retired entirely; the binary's only DB-location source is workspace discovery (or the explicit `--db` flag).

The migration shipped in two passes: a first attempt that was reverted (`63f8327`) when the e2e harness picked up the dogfood DB and corrupted it, then the layered-harness rebuild and a second cutover that landed clean. The retrospective at `docs/retrospectives/v0.13-architecture-audit.md` records the testing gap that surfaced and the harness primitives that closed it.

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Event log transactionality | Same `WriteTx` as the row write | An event without a row (or vice versa) is structurally impossible |
| Event payload shape | Typed structs + `UnknownPayload` fallback | Round-trip safety across version skew during portability import |
| UDA Schema Validation scope cut | Replaced with first-class `level` field | Self-host only needed taxonomy; generic UDA validator was weeks of work for no dogfood payoff |
| Per-project taxonomy is ordered list | Not a tree, not a free-form set | Parent-child constraint is rank-based, not membership-based |
| Sibling `order` is `REAL` | Float midpoint math | Insert between siblings without renumbering; `Resequence` is the recovery path |
| Move + reparent in one statement | `UpdateOrderAndParent` | Re-parent and re-order must commit atomically or the cycle check is meaningless |
| Cycle check via descendant scan | One recursive CTE | Cheap relative to the move itself; correctness over micro-optimization |
| Override resolution: nearest ancestor | Walk up until first non-empty | Lets a milestone-level pin propagate without forcing every node to opt in |
| RFC 7396 merge-patch on `urgency_overrides` | `null` deletes a key, absent unchanged | Matches existing tag-update semantics; `_clear` flag for wholesale reset |
| Rollup in Go, not SQL | `domain.AggregateRollup` is pure | Filter pipeline is already Go-side; SQL aggregation would fork the rollup off the filter contract |
| Filter dual role in `summary` | Filter scopes both block selection AND descendant counting | `level=story` naturally means "per-story rollup of stories under each story" |
| Strict-descendants in rollup | Self excluded | The root's own status answers a different question; the rollup describes "the work below it" |
| Default mode for portability import | Fail-fast on collision | `--replace` and `--truncate` are explicit opt-ins; default never destroys data |
| Single-tx apply on import | All-or-nothing | A partial workspace is worse than no workspace |
| CSV deferred | Tracked as future work | JSON satisfies the dogfood path; CSV is for downstream tooling we haven't validated yet |
| `ROADMAP.md` is generated, not edited | `make roadmap` regenerates atomically | Source of truth is the tusk DB; the file is a derived artifact |
| Project description in `> ` blockquote | Markdown-canonical | Renders as a description in every standard MD viewer |
| Inline metadata tokens after task name | Same lexer as inline-field CLI | Single grammar across read and write surfaces |
| Repo-root `tusk.toml` + `.data/tusk.db` | Workspace lives with the code | Self-host means the roadmap travels in the same git tree as the code that satisfies it |
| Layered e2e harness | `Env` / `MCPEnv` over `t.TempDir()` | Walk-up tests cannot see the dogfood DB; corruption from harness leakage is structurally prevented |
| Drop `TUSK_DB` env var | Workspace discovery is canonical | One source of truth for DB location avoids the layering bug that bit the first cutover attempt |

### Known Limitations

- Sibling `order` is a float; very long sibling chains with repeated insertions can exhaust gap precision and require `tusk task resequence`. The CLI surfaces `ErrOrderGapExhausted` with the parent short ID so the recovery path is one command away.
- `urgency_overrides` is per-task at the storage level; there is no project-wide override surface in v0.13. Roadmap-wide urgency tuning still goes through the global config file.
- The markdown renderer does not emit `--rollup` data; rollup output is text/JSON only.
- The portability codec does not preserve event-row primary keys; events round-trip by content but not by ID. Adequate for backup/restore, insufficient for cross-instance event correlation.
- The `tusk-roadmap` workspace is the only project that drives `make roadmap`; multi-project markdown trees are explicitly rejected.
- The first repo-root-workspace cutover attempt corrupted the dogfood DB. The post-fix harness primitives prevent recurrence, but anyone reverting past `c6f26a5` should expect the same class of issue if they do not also revert the harness migration.
