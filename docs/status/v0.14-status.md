## What Was Built

v0.14 establishes a project-wide naming and spacing convention for the Tusk codebase, enforces it mechanically with a custom Go static-analysis multichecker, and sweeps every existing package to match. **No behavior changes** — pure readability and tooling.

The milestone shipped in eight phases plus a follow-up sweep:

- **P1** — convention doc (STYLE.md), linter scaffold (`cmd/tusk-lint`), and rule 1 enforcement (`varnamelen`).
- **P2** — three custom analyzers (rules 2, 3, 4) wrapped into the `tusk-lint` multichecker.
- **P3** — sweep `service/` (~1,576 violations).
- **P4** — sweep `internal/tui/` (~954 violations).
- **P5** — sweep `internal/mcp/` and `internal/portability/` (~811 violations).
- **P6** — sweep `filter/`, `domain/`, and `syntax/` (~339 violations).
- **P7** — sweep `repository/`, `sqlite/`, `cmd/`, `tests/e2e/`, and the repository root (~1,627 violations).
- **P-CONFIG** — follow-up sweep for `config/` (caught in audit; not in the original spec).
- **P8** — lock-in: structural regression guards, `make lint-style-locked` CI target, STYLE.md status header.

After P8 closes, every package in the repository is in compliance with all four STYLE.md rules. `.golangci.yml` carries no per-package `varnamelen` exclusions, the custom-analyzer pathfilter slice is empty, and `make lint-style-locked` guards both escape hatches in CI.

## The Four Rules

The convention is captured as four numbered, linter-enforced rules. STYLE.md is the canonical reference; the table below is a one-line summary plus the tool that enforces it.

| Rule | Description | Enforced by |
|------|-------------|-------------|
| 1 | No single-character identifiers anywhere — locals, range vars, parameters, receivers, loop indices, generic type parameters, **package names, and file names**. There are no exemptions, including `*testing.T`, `*testing.B`, `testing.TB`, short generic type parameters, and the analysistest stdlib convention of single-letter testdata packages. | `varnamelen` (golangci-lint) |
| 2 | Blank lines around `if err != nil` guards — the assignment, the guard, and the next statement are visually separated. | `tusk-lint -blankline` |
| 3 | Named errors on `err` shadow — when two or more `err` variables are declared at the same lexical scope, **every** instance (including the first) uses a typed name (`<noun>Err`). | `tusk-lint -namederr` |
| 4 | Standardized test-handle parameter names — `*testing.T` → `test`, `*testing.B` → `bench`, `testing.TB` → `harness`. Deviation fails the build. | `tusk-lint -testhandle` |

Plus an advisory style guide for cases the linter cannot mechanically check (receiver naming conventions, generic type parameter taste, loop-index defaults, single-error functions).

## Key Features in Detail

### `cmd/tusk-lint` Multichecker

`cmd/tusk-lint` is a thin shell over `multichecker.Main(...)`. Each analyzer is a `*analysis.Analyzer` registered by name (`blankline`, `namederr`, `testhandle`). The `-disable` and analyzer-specific flags inherit from the upstream `analysis` framework, so a contributor can run a single analyzer in isolation:

```bash
go run ./cmd/tusk-lint -blankline ./service/...
go run ./cmd/tusk-lint -namederr  ./internal/...
```

The default invocation (`go run ./cmd/tusk-lint ./...`) runs all three. `make lint-tusk` wraps that.

### `pathfilter` Helper

Originally introduced to provide a per-package exclusion mechanism for the custom analyzers — symmetric with golangci-lint's `linters: [varnamelen]` rules — the helper lets each analyzer short-circuit on packages still in the sweep queue. Each phase (P3–P7 + P-CONFIG) removed its package's regex from the helper alongside its golangci-lint rule.

By the end of P8, the `excluded` slice is empty:

```go
var excluded = []*regexp.Regexp{}
```

The helper and its `Excluded(pkgPath)` function are kept in place so future per-package rollouts can reuse the bridge code without re-introducing it; lock-in is enforced via `make lint-style-locked`, not by deleting infrastructure.

External test packages (Go's `package foo_test` convention) produce a pkgPath ending in `_test`. The helper trims that suffix before matching so a test file in `sqlite_test` is governed by the same exclusion as the `sqlite` production package. (P2-T4 amendment, preserved for future use.)

### `make lint-style-locked` (Structural Regression Guard)

The lock-in target fires before `lint-go` and `lint-tusk` and fails CI if either escape hatch tries to reintroduce `varnamelen` suppression:

1. A `//nolint:varnamelen` directive in any tracked Go source file (matched via `git ls-files '*.go' | grep '//[[:space:]]*nolint:[a-zA-Z0-9_,-]*varnamelen'` so `.go-cache/` and `bin/` cannot produce false positives).
2. A `linters: [varnamelen]` exclusion rule in `.golangci.yml`.

Each failure prints the offending file:line and instructs the contributor to **rename the identifier** rather than suppress the linter. The fix for a `varnamelen` violation is always renaming, never suppression — that is the convention's point.

### Sweep Methodology

Each sweep phase followed the same three-task pattern:

- **T1** — drop the package's `varnamelen` exclusion rule from `.golangci.yml`.
- **T2** — drop the package's regex from `internal/lint/pathfilter/pathfilter.go`.
- **T3** — apply the four STYLE.md rules to every file in the package.

Counterintuitively, **T3 (apply fixes) ran BEFORE T1/T2 (drop exclusions)** within each phase — the opposite of the spec's stated order. This kept CI green between PRs: applying fixes without dropping exclusions is a no-op for CI; dropping exclusions before fixes are in is an immediate red. The order swap meant every per-task PR landed cleanly without batched merges.

T3 was further split into per-file or per-bucket sub-tasks (T3a, T3b, …) sized so each PR review was reasonable. The largest phase (P3, `service/`, ~1,576 violations) split T3 into ten buckets; the smallest (P6, `syntax/` and `domain/`) into four.

### The Hard Rule on Naming

> Use full descriptive words, not 2-character abbreviations.

Implementer subagents repeatedly drifted toward terse abbreviations during sweeps (`wf`, `evt`, `tc`, `tr`, `ch`, `dom`, `def`, `pp`, `lp`, `fp`, `ff`, `fl`). The user feedback was consistent: `wf is not that descriptive`, `tc is not descriptive`. The orchestration prompt was hardened with an explicit forbidden-list and a mandatory grep self-check before commit. Even with that, several sweep PRs needed cleanup commits to replace residual abbreviations.

The advisory style guide section in STYLE.md captures the principle in non-mechanical form for future contributors: **role-named identifiers** (`service`, `renderer`, `app`) over abbreviations; qualified names when two services share a scope (`taskService` / `projectService`); `index` for the outermost loop, `subindex` for nested.

### The P-CONFIG Follow-Up

The original v0.14 spec listed seven sweep phases (P3–P7) covering every package the audit had identified. During the P8 dry run, `config/` surfaced as a package with violations that no phase had targeted — it had been overlooked entirely. Rather than retrofit P7's scope or push the lock-in past the milestone, the work was tracked as P-CONFIG: a follow-up sweep with the same T1/T2/T3 shape that ran independently. It shipped as commit `83e8a0e` and was the last sweep before P8 entered.

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Naming conventions in code or in docs | Both — STYLE.md is the reference, the linters are the enforcer | Mechanical enforcement prevents regression; doc captures the *why* and the advisory cases linters cannot reach |
| Ship as one milestone | Eight phases over ~3 days | Mid-flight phases left CI red intermittently; fewer phases would have meant a larger merge surface; the eight-phase split kept each PR small enough for human review |
| `varnamelen` for rule 1 | Existing golangci-lint linter | Mature, configurable, free; building a custom analyzer for the same job would have been pure NIH |
| Custom analyzers for rules 2-4 | Three small `analysis.Analyzer` impls | golangci-lint had nothing equivalent; rules are precise enough to encode in an AST visitor |
| Multichecker over per-binary | One `cmd/tusk-lint` ships all three | Simpler `make lint-tusk`, cheaper analysis (single load pass), single place to add a fourth rule |
| Bridge code via `pathfilter` helper | Per-package short-circuit; symmetric with golangci-lint exclusions | Lets phases ship sequentially without breaking previously-clean packages; code stays in place after lock-in for any future per-package rollouts |
| `_test` suffix trimming in pathfilter | `strings.TrimSuffix(pkgPath, "_test")` | External test packages (`package sqlite_test`) should be governed by the production package's exclusion |
| Ordering within sweep phases | T3 (apply) before T1/T2 (drop exclusions) | Opposite of spec; keeps CI green between PRs — applying fixes is a no-op for CI, dropping exclusions before fixes is immediate red |
| Sweep phase split | Ten buckets for the largest, four for the smallest | Each per-task PR sized for a reasonable human review |
| `lint-style-locked` runs first in `lint` | Cheap structural check before slow analysis | Fail-fast on the most regressive class of error |
| Source scan via `git ls-files` | Not raw `find` or `grep` | `.go-cache/` contains `.go` files that should never be inspected; tracked-files-only avoids that class of false positive |
| The fix for varnamelen is always rename | `//nolint:varnamelen` is forbidden | The convention's point is that two-character minimums are universally readable; suppression undermines the rule |
| Helper kept after lock-in | `excluded` slice is empty but the file stays | Future per-package rollouts can reuse the bridge code; lock-in is enforced by `make lint-style-locked`, not by deletion |
| P-CONFIG as a follow-up, not retrofit | Tracked separately, shipped before P8 | Avoided rewriting P7's scope mid-milestone; lock-in had a clean "all sweeps done" precondition |
| STYLE.md status header on lock-in | "enforced repository-wide as of v0.14" | Future contributors learn from STYLE.md alone that the rules are mechanical, not aspirational |
| One PR per task | ~93 PRs over the milestone | Each merge was reviewable in isolation; rebase-merge only repo means stacked PRs were the dependency mechanism |

### Known Limitations

- The advisory style guide in STYLE.md is intentionally not enforced. Receiver-naming taste, generic-type-parameter taste, and loop-index conventions remain review-time guidance. A future milestone could promote individual sub-rules to mechanical enforcement if a counterexample pattern emerges.
- `pathfilter.Excluded(pkgPath)` is dead code in the post-lock-in state — `excluded` is empty so the function always returns false. The infrastructure is kept deliberately for future per-package rollouts; lock-in is enforced by `make lint-style-locked` rather than by deleting the helper.
- Rule 4 (test-handle parameter names) is enforced at the parameter site only — it does not check that field names on per-test struct types follow the same convention. In practice the codebase does not use such struct types.
- The blankline analyzer (rule 2) targets `if err != nil` guards specifically; other guard shapes (`if cond {`, `if !ok {`) are not covered. The convention is silent on those.
