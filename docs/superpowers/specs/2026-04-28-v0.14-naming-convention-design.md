# v0.14 — Naming and Spacing Convention

> Date: 2026-04-28
> Milestone: v0.14
> Status: design (pending review)
> Related: [v0.13 architecture audit](../../retrospectives/v0.13-architecture-audit.md), [v0.13 retrospective](../../retrospectives/v0.13-roadmap-migration.md)

## Goal

Establish a project-wide naming and spacing convention for the Tusk
codebase, enforce it mechanically with a linter, and clean every
existing package to match. The v0.13 architecture audit observed that
single-character locals, dense unspaced blocks, and shadowed `err`
variables compound to make hot files hard to scan and review. v0.14
fixes that as its sole milestone theme — no behavior changes; pure
readability and tooling.

The milestone is decomposed into eight stories so each ships
independently and the work is unlikely to slip.

## Scope

**In scope.** A written convention (`STYLE.md`), a custom linter
binary (`cmd/tusk-lint`) packaging three `go/analysis` analyzers,
configuration of the existing golangci-lint pipeline to enforce a
fourth rule via `varnamelen`, and per-package sweeps that bring every
file in the repository into compliance.

**Out of scope.** Anything from the v0.13 architecture audit that
isn't naming or spacing — service-layer decomposition, multi-bundle
decision, parser hardening, traceability matrix, atomic-write rule,
process guards, domain reorg. Those land in v0.15 through v0.19 and
are tracked separately. Behavior changes of any kind.

## Section 1 — Convention content

The convention establishes four mechanical rules and a small style
guide. The rules are linter-enforced; the style guide is review-time
guidance that addresses common rename-target decisions once instead
of debating them per PR.

### Rule 1 — No single-character identifiers anywhere

Locals, range variables, function and method parameters, receivers,
loop indices, and generic type parameters all require ≥2 characters.
There are no exemptions, including `*testing.T`, `*testing.B`,
`*testing.TB`, and short generic type parameters.

```go
// before
for _, t := range tasks {
    if t.WaitUntil != nil { ... }
}

// after
for _, task := range tasks {
    if task.WaitUntil != nil { ... }
}
```

```go
// before
func (s *TaskService) Create(ctx context.Context, t *domain.Task) error

// after
func (service *TaskService) Create(ctx context.Context, task *domain.Task) error
```

**Enforcement:** `varnamelen` in golangci-lint with
`min-name-length: 2`, `check-receiver: true`, `check-return: true`,
`check-type-param: true`, and an empty `ignore-names` list. Exclusions
are path-based only and shrink to empty by Story 8.

### Rule 2 — Blank lines around `if err != nil` guards

An error-producing assignment is separated from its guard by a blank
line, and the guard's closing brace is separated from the next
statement by another blank line. Dense unspaced blocks make
single-letter or short identifiers easier to lose visually; even with
rule 1 in place, the spacing still matters.

```go
// before
project, err := projectRepo.GetByID(ctx, id)
if err != nil {
    return nil, fmt.Errorf("looking up project: %w", err)
}
return project.ID, nil

// after
project, err := projectRepo.GetByID(ctx, id)

if err != nil {
    return nil, fmt.Errorf("looking up project: %w", err)
}

return project.ID, nil
```

**Enforcement:** custom analyzer at `internal/lint/blankline/`.

### Rule 3 — Named errors on `err` shadow

When two or more `err` variables are declared at the same lexical
scope, **every** instance — including the first — must use a typed
name (`<noun>Err`). Sequential `err :=` shadows hide the failure
mode at the variable; named errors document it. Renaming all
instances rather than leaving the first as `err` keeps the block
visually uniform — readers don't have to track which slot is which.

```go
// before — service/task.go:325–339
blockingCounts, err := bundle.Relations.CountBlockingByTasks(ctx, taskIDs)
if err != nil {
    return nil, fmt.Errorf("loading blocking counts: %w", err)
}
blockedByCounts, err := bundle.Relations.CountBlockedByTasks(ctx, taskIDs)
if err != nil {
    return nil, fmt.Errorf("loading blocked-by counts: %w", err)
}
annotationCounts, err := bundle.Annotations.CountByTasks(ctx, taskIDs)
if err != nil {
    return nil, fmt.Errorf("loading annotation counts: %w", err)
}

// after
blockingCounts, blockingErr := bundle.Relations.CountBlockingByTasks(ctx, taskIDs)

if blockingErr != nil {
    return nil, fmt.Errorf("loading blocking counts: %w", blockingErr)
}

blockedByCounts, blockedByErr := bundle.Relations.CountBlockedByTasks(ctx, taskIDs)

if blockedByErr != nil {
    return nil, fmt.Errorf("loading blocked-by counts: %w", blockedByErr)
}

annotationCounts, annotationErr := bundle.Annotations.CountByTasks(ctx, taskIDs)

if annotationErr != nil {
    return nil, fmt.Errorf("loading annotation counts: %w", annotationErr)
}
```

A function that produces exactly one `err` keeps it named `err` —
this rule fires only on shadow.

**Enforcement:** custom analyzer at `internal/lint/namederr/`.

### Rule 4 — Standard test-handle parameter names

Functions and methods that take a testing handle must use a
standardized parameter name:

| Type            | Required name |
|-----------------|---------------|
| `*testing.T`    | `test`        |
| `*testing.B`    | `bench`       |
| `testing.TB`    | `harness`     |

Deviation fails the build. The list is finite and lives in the
analyzer's source.

```go
// before
func TestRunCreate(t *testing.T) { ... }

// after
func TestRunCreate(test *testing.T) { ... }
```

**Enforcement:** custom analyzer at `internal/lint/testhandle/`.

### Style guide (advisory)

The linter does not enforce these — they're review-time guidance for
cases where the right name depends on context.

- **Receivers** use a role word matching the type: `*TaskService` →
  `service`, `*Renderer` → `renderer`, `*App` → `app`. When two
  service types appear in the same scope, qualify:
  `taskService` / `projectService`. Receiver names are consistent
  within a file, never per-method.
- **Generic type parameters** use role-named identifiers: `Element`,
  `Item`, `Key`, `Value`, `Result`. Never single letters (rule 1
  already enforces ≥2 chars; the role-naming is taste).
- **Loop indices** use `index` for outermost, `subindex` for nested,
  or contextual names (`row` / `col`, `phase` / `step`).
- **Errors in single-error functions** stay `err`. Rule 3 fires only
  on shadow.

## Section 2 — Doc location and linter packaging

### Convention doc

`STYLE.md` lives at the repo root and is the canonical reference for
the convention. `CONTRIBUTING.md` gains a one-line cross-reference:
"For code style, see [STYLE.md](STYLE.md)." STYLE.md is structured
as: rules first (each with rationale and example), style guide
second, enforcement summary third.

`STYLE.md` is favored over a `CONTRIBUTING.md` section because the
convention is substantial (four rules + style guide + rationale +
examples), CONTRIBUTING.md is already ~10 KB, and a top-level
`STYLE.md` is easy to link from PR templates and review checklists.

### Linter binary

```
cmd/tusk-lint/
  main.go                    # multichecker entry; registers all analyzers
internal/lint/
  blankline/
    analyzer.go               # rule 2
    analyzer_test.go
    testdata/src/a/a.go       # standard go/analysis testdata layout
  namederr/
    analyzer.go               # rule 3
    analyzer_test.go
    testdata/...
  testhandle/
    analyzer.go               # rule 4
    analyzer_test.go
    testdata/...
```

`cmd/tusk-lint/main.go` calls
`multichecker.Main(blankline.Analyzer, namederr.Analyzer, testhandle.Analyzer)`.
Each analyzer is independently runnable via flags
(`tusk-lint -blankline ./...`).

Path filtering is implemented uniformly across all three analyzers
through a shared helper that reads an exclude list. Exclusion entries
match by package import path prefix.

### golangci-lint config

`.golangci.yml` enables `varnamelen` (rule 1) with strict settings.
The exclusions block is the v2 schema as used in the existing config
(rules live under `linters.exclusions.rules`):

```yaml
version: "2"

linters:
  enable:
    - varnamelen
  exclusions:
    rules:
      # existing errcheck rules stay
      - linters: [errcheck]
        path: _test\.go
      - linters: [errcheck]
        text: 'Error return value of `.*\.Close` is not checked'
      # new — full-codebase exclusion shrinks per sweep
      - linters: [varnamelen]
        path: ^(service/|internal/tui/|internal/mcp/|filter/|domain/|repository/|sqlite/|cmd/|tests/e2e/|client\.go$)

linters-settings:
  varnamelen:
    min-name-length: 2
    check-receiver: true
    check-return: true
    check-type-param: true
    ignore-names: []
    ignore-decls: []
```

The `path` regex is the rollout state. Each sweep PR shrinks the
alternation; Story 8 removes the `varnamelen` rule entirely (the
`errcheck` rules stay). Anchored slashes (`service/` not `service`)
prevent accidental matches against directories that share a prefix.

### Makefile

```makefile
lint: lint-go lint-tusk

lint-go:
	golangci-lint run ./...

lint-tusk:
	go run ./cmd/tusk-lint ./...
```

Existing CI runs `make lint`; both linters land through that single
hook.

## Section 3 — Rollout strategy

Three phases. Every PR is individually reviewable and CI never breaks
unexpectedly because each PR adds in-scope coverage and the
violations are fixed in the same PR.

### Phase A — Tooling lands (Stories 1 and 2)

Phase A ships the convention doc, linter binary, all four rules, and
configures path exclusions covering every directory currently in the
repo. CI runs both linters but finds nothing in scope. Zero behavior
change to the codebase; pure infrastructure.

### Phase B — Per-package sweeps (Stories 3–7)

One PR per package (or per file if a package's diff exceeds
review-friendly size). Each sweep PR:

1. Removes the package from the `varnamelen` path exclusion in
   `.golangci.yml` and from the path filter in each tusk-lint analyzer.
2. Fixes every violation the linters now flag.
3. References STYLE.md in the PR body so reviewers can verify against
   documented rules.

Recommended sweep order:

1. `service/` — largest, highest-traffic; proves the convention.
2. `internal/tui/`
3. `internal/mcp/`
4. `filter/` + `domain/`
5. `repository/` + `sqlite/` + `cmd/` + `tests/e2e/` + root files

Test files travel with their production package (so
`service/task_test.go` sweeps in the `service/` PR). Sweeps 3–7 can
land in any order — they're independent.

### Phase C — Lock-in (Story 8)

After every sweep lands, one cleanup PR:

1. Removes the now-empty exclusion lists from `.golangci.yml` and
   each tusk-lint analyzer.
2. Adds a CI assertion that the exclusion lists stay empty — guards
   against future PRs adding `// nolint:varnamelen`, expanding the
   exclude regex, or otherwise re-loosening the rules.

The convention is now structurally protected.

### Why this shape

- Each sweep PR is self-contained; reviewable in isolation.
- CI never breaks unexpectedly: leaving the exclusion list and
  fixing the violations are atomic in the same PR.
- Rollout state is grep-able at any time —
  `cat .golangci.yml | grep -A 10 exclusions` shows what's still
  pending.
- Phase A means contributors can run `make lint-tusk` locally on
  their branches throughout the milestone and see violations even in
  not-yet-swept packages (advisory output), so new code can
  voluntarily ship clean ahead of its package's sweep.

### Open trade-off

During the rollout, new code added to a not-yet-swept package can
technically land with violations because that package is still
excluded. We're punting on tightening this: the bounded duration of
the milestone keeps exposure small, and a "changed-lines-only" gate
would burn engineering time on transitional infrastructure that
disappears at lock-in. Flagged so future contributors aren't surprised.

## Section 4 — Story breakdown

Eight stories. Stories 1, 2, and 8 are gated; Stories 3–7 can land
in any order.

### Story 1 — Convention doc + linter scaffold + rule 1

- `STYLE.md` at repo root with the four rules and the style guide.
- One-line cross-reference added to `CONTRIBUTING.md`.
- `cmd/tusk-lint/main.go` with the `multichecker` shell (no
  analyzers registered yet).
- `Makefile` `lint-tusk` target wired into `make lint`.
- `varnamelen` configured in `.golangci.yml` with strict settings
  and a path exclusion covering every directory.
- Verify CI is green against the unmodified codebase.

### Story 2 — Custom analyzers (rules 2, 3, 4)

- `internal/lint/blankline/analyzer.go` (rule 2) with testdata.
- `internal/lint/namederr/analyzer.go` (rule 3) with testdata.
- `internal/lint/testhandle/analyzer.go` (rule 4) with testdata
  including the hardcoded type→name table.
- All three registered in `cmd/tusk-lint/main.go`.
- Path exclusions still cover every directory; CI green.

### Story 3 — Sweep `service/`

Highest-traffic package. Includes `service/*_test.go`. If the diff
exceeds review-friendly size, split per-file (`task.go`,
`task_test.go`, `project.go`, ...). Milestone scales to however many
sub-PRs the actual diffs warrant.

### Story 4 — Sweep `internal/tui/`

Includes `commands.go` (1450 LoC), `render.go` (1231 LoC), all other
tui files, and tests.

### Story 5 — Sweep `internal/mcp/`

Includes `tools.go` (1729 LoC), all per-tool handler files, and tests.

### Story 6 — Sweep `filter/` + `domain/`

Smaller, more numerous files. Bundling them prevents story-count
inflation.

### Story 7 — Sweep `repository/` + `sqlite/` + `cmd/` + `tests/e2e/` + root

Last bucket — all remaining production and test code, including
`client.go` and the e2e harness.

### Story 8 — Lock-in

- Remove the `varnamelen` exclusion rule from `.golangci.yml`. The
  existing `errcheck` rules stay — this is a targeted removal, not a
  block deletion.
- Remove the now-empty path-filter exclude lists from each tusk-lint
  analyzer.
- Add a CI assertion that no `// nolint:varnamelen` directives appear
  anywhere in the tree, and that `.golangci.yml` contains no
  `linters: [varnamelen]` exclusion rule. Regression guard against
  excludes regrowth.

## Dependencies and ordering

```
Story 1 ──▶ Story 2 ──▶ Stories 3..7 ──▶ Story 8
                       (any order, parallelizable)
```

Story 1 must land before Story 2 (the multichecker shell exists
before analyzers register into it). Story 2 must land before any
sweep so the custom rules are present when packages enter scope.
Stories 3 through 7 are mutually independent — different contributors
can take them in parallel. Story 8 lands once every sweep is
complete; the empty-exclusions assertion makes the milestone's done
state structurally verifiable.
