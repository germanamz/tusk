## What Was Built

v0.7 adds player state management — humans and AI agents self-register as players, claim tasks to prevent overlapping work, and use an atomic task queue to pop the next highest-urgency available task in a single operation. Players are persisted to the database with liveness tracking, and all claiming semantics enforce optimistic locking.

## Key Features in Detail

### Player Registration

Players self-register by providing an ID on any action. No predefined roster needed. The `--player` CLI flag and `player_id` MCP parameter trigger auto-registration on first use. Explicit registration is also available via `tusk player register`.

Players have a `type` field (`human` or `agent`) and a `last_seen_at` timestamp updated on every action.

### Task Claiming

Claiming prevents overlapping work between players:

- **Explicit claim** — `tusk claim <id>` reserves a task
- **Auto-claim on start** — `tusk start` claims if unclaimed, rejects if claimed by another
- **Idempotent re-claim** — claiming a task you already own is a no-op
- **Release** — only the current claimant can release
- **No force-steal** — if a player goes stale, managing that is the consumer's responsibility
- **Claims preserved** — `done` and `delete` keep `claimed_by` for historical attribution

### Task Queue

`tusk pop` atomically finds the highest-urgency available task, claims it for the player, and starts it:

1. Calls `Available` to get urgency-ranked candidates
2. "Available" means: unclaimed + `pending` or `active` status + not blocked by incomplete tasks + not waiting
3. Attempts `Claim` + `Start` on the top candidate
4. On `ErrTaskClaimed` or `ErrConflict` (race condition), retries with the next candidate
5. Returns the single claimed+started task, or `ErrNoAvailableTasks`

The "not blocked" check uses `CountBlockedByIncompleteTasks`, which JOINs relations with tasks to only count blockers that are still incomplete (status not `completed` or `deleted`). A completed blocker no longer prevents the target from being available.

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Player identity | Self-declared string ID | Consumers own their naming; no resolution burden for identifiers tusk doesn't control |
| Claim conflict | Hard reject (`ErrTaskClaimed`) | Stale player management is the consumer's concern; simple and predictable |
| Claims on done/delete | Preserved (not auto-released) | Historical attribution — who completed the task matters |
| Pop atomicity | Optimistic retry loop | Consistent with existing concurrency model; urgency scoring stays in Go |
| "Not blocked" semantics | Only count incomplete blockers | Completed/deleted blockers don't prevent a task from being actionable |
| Pop claims + starts | Both in one operation | Minimizes round-trips for agents; finer control available via separate claim/start |
| Available scope | pending + active | Active-but-unclaimed tasks are legitimate candidates (e.g., released mid-work) |
| Waiting filter in Available | Excluded | Matches `tusk next` behavior; wait_until tasks are not actionable |

### Known Limitations

- **No pagination** — `tusk list` and `tusk available` return all matching tasks
- **UDA values are untyped** — all values stored as strings; typed UDA validation deferred to v0.9
- **No force-steal or TTL on claims** — stale player management is the consumer's responsibility
- **Pop re-lists on every call** — does not cache the available list between retries; acceptable for typical task counts
- **Urgency sigmoid constants not configurable** — k and midpoint are internal; only weights are configurable
