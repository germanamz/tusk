# v0.13 — Roadmap Self-Host

> The v0.13 milestone is **in progress**. This file accumulates per-initiative release notes as each one lands. See `ROADMAP.md` for the full milestone scope.

## Progress Rollup

Static CLI summary views for per-subtree completion tracking. Two new surfaces — `tusk task tree --rollup` and `tusk task summary` — plus a mirroring `tusk_task_summary` MCP tool. The math leverages the v0.9 status-role system (`done`, `delete`) so custom workflows participate without configuration. Live event-log-driven dashboards remain deferred to v0.15.

### Highlights

**Domain aggregator (`domain.AggregateRollup`)**
- Pure function: `(descendants []*Task, workflowFor func(*Task) *Workflow) Rollup`
- Per-task workflow classification — `delete`-role tasks excluded entirely; `done`-role tasks count toward both `Done` and `Total`
- Multi-workflow descendants merge by status name; first-seen ordering across workflows; seed workflow's full status order pre-populated with zeros
- Counts honor highlight/dim role styling on render

**Service primitives**
- `TaskService.SummarizeSubtree(ctx, rootID)` — strict-descendant rollup of a single task
- `TaskService.SummarizeBlocks(ctx, blockFilter, full)` — selects block tasks via filter, rolls up each subtree; `full=false` scopes descendants to the same filter, `full=true` keeps the whole subtree
- Block sort: urgency desc, short_id ascending tiebreaker
- Tag predicates in `blockFilter` honored on the descendant pass via batch tag-fetch in `EvalFilter`

**`tusk task tree --rollup`**
- Branch nodes append `[done/total done, %]  (status: count, ...)` after the existing line
- Workflow-defined status order; zeros included; `delete`-role buckets excluded
- `–%` printed when `Total == 0`
- Always fetches the full subtree (decoupled from `--all`) so descendants under a `delete`-role ancestor still contribute to totals
- `--all` controls visibility only; `delete`-role nodes are pruned from rendering when `--all` is off, but rollup numbers stay accurate
- JSON: every node carries `rollup` when the flag is set (uniform shape across leaves and branches); shape is byte-stable when the flag is off

**`tusk task summary` CLI**
- `tusk task summary <short_id>` — single subtree mode
- `tusk task summary <filter...>` — filter mode; one block per matching task; filter scopes both block selection AND descendant counting
- `tusk task summary` — workspace-wide (blocks = root tasks)
- `--full` decouples descendant scope from block selection; rejected with a usage error in single-id and roots modes
- Text mode: multi-line label-padded blocks, separator `────`, `TOTALS` line in filter/roots modes; empty result prints `No tasks matched.` to stderr with exit 0
- JSON envelope: `{mode: "single"|"filter"|"roots", blocks: [...], totals?: {...}}` — `totals` omitted in single mode; always emitted in filter/roots mode (zero rollup when no blocks)

**`tusk_task_summary` MCP tool**
- Mirrors `tusk_task_list`'s structured-param surface plus `short_id`, `level`, and `full`
- Param precedence: `short_id` > `filter` string > structured params > none
- `short_id` + `full=true` → `INVALID_ARGUMENT: full is not valid in single-id mode`
- `filter` parse error surfaces the parser's message verbatim
- Response envelope identical to the CLI JSON shape; `task` fields populated through the existing `toTaskResponse(...)` path
- `buildTaskFilter` extracted from `handleTaskList` into a shared helper (now driving both list and summary)

**Custom workflow support**
- A workflow whose `done` role lives on a non-`completed` status (e.g. `shipped`) flows correctly through every layer
- A workflow without a `done` role is legal — `Done` stays 0, `Total` reflects non-`delete` tasks

### Breaking Changes

None. `tusk task tree` without `--rollup` and every other CLI / MCP surface remain byte-identical to pre-v0.13. The new `--rollup` flag, the `summary` subcommand, and `tusk_task_summary` are all additive.

### Usage

```bash
# Tree with branch progress badges
tusk task tree --rollup
tusk task tree --rollup --all                # include delete-role nodes in rendering

# Single subtree summary
tusk task summary a3f8b2c1
tusk task summary a3f8b2c1 --format json

# Filter-scoped: per-story rollup of stories
tusk task summary level=story
tusk task summary level=story --full         # blocks = stories; full subtree counted

# Workspace-wide (blocks = root tasks)
tusk task summary
tusk task summary --format json

# Tag-scoped (descendant counts honor +urgent on the in-memory pass)
tusk task summary +urgent
```

### Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Where the math lives | Pure `domain.AggregateRollup` + thin service composition | Reused by `tree --rollup` (already-fetched tasks) and `task summary` (service-fetched); avoids forking the math |
| In-memory vs SQL aggregation | In-memory | Filter pipeline is already Go-side; SQL aggregation would fork the rollup off the filter contract |
| Self-inclusion | Strict descendants only | The root's own status answers a different question; the rollup describes "the work below it" |
| Filter dual role | Filter scopes both block selection AND descendant counting by default | `level=story` naturally means "per-story rollup of stories under each story" |
| `--full` escape hatch | Decouples descendant scope from block selection | Required to express "blocks at this level, full subtree counted" without sacrificing the dual-role default |
| Status breakdown ordering | Workflow-defined; zeros included; `delete`-role excluded | Stable visual width, matches workflow's intended sequence |
| Multi-workflow buckets | Merge by status name | The user-visible label is what matters; `(workflow, name)` keying surfaces a distinction users don't have a vocabulary for |
| Tree `--rollup` fetch path | Always fetch full subtree | Decouples `--all` (visibility) from `--rollup` (computation); prevents underreporting under delete-role ancestors |
| MCP input shape | Mirror `tusk_task_list` precedence | Agents stay in the structured-input regime by default; power cases remain expressible |
| Workspace-wide totals line | Always emit in multi-block modes | Predictable shape across `roots` and `filter` modes |
| Tag predicates on the descendant pass | Batch-fetch via `bundle.Tags.GetTaskTagsBatch` only when the filter references Tags | Avoids the round-trip for level/priority/status filters |
| RootID predicate on the descendant pass | Documented match-all | Descendants of a block already matching `tree=X` are transitively under X; honoring the predicate again would just walk ancestry |
