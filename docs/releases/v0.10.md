# v0.10 — Datastore-Backed Projects & Workflows

Move projects and workflows out of the TOML config file and into the workspace database. Tasks already lived in SQLite; after v0.10, every mutable workspace entity does. The user-facing CLI, inline syntax, and MCP tools are unchanged — only the write target moves.

### Highlights

**Projects and Workflows as First-Class Entities**
- `projects` and `workflows` tables in SQLite, seeded by migrations
- UUID `id`, human-readable `name`, `version` for optimistic locking, `created_at` / `updated_at` — same shape as `tasks`
- `tasks.project_id` is now a real foreign key with `ON DELETE RESTRICT`
- `projects.workflow_id` is a foreign key with `ON DELETE RESTRICT`
- `project.settings` is a JSON blob carrying `auto_complete`, `auto_revert`, and `urgency` overrides
- `workflow.statuses` and `workflow.transitions` are JSON blobs; role schema preserved from v0.9

**Service Layer Owns the Writes**
- `ProjectService.Create / Modify / Delete / List / Get` calls `ProjectRepository` directly
- `WorkflowService.Create / Modify / Delete / List / Get` calls `WorkflowRepository` directly
- Optimistic locking: callers fetch to read `version`, mutations pass it back, conflicts surface as `domain.ErrConflict`
- Role-schema validation (exactly one `initial`, one `start`, ≥1 `terminal`, one `done`, one `delete`) moved out of `config.Validate` into `WorkflowService`
- Project delete guard (reject `default`, reject when tasks reference, `--force` bypass) stays at the service boundary and runs before the DB delete

**Config Schema Trimmed to Globals**
- `[projects.*]` and `[workflows.*]` removed from `config/default.toml`
- `config.Config.Workflows` / `.Projects` fields removed
- `config.WorkflowConfig`, `ProjectConfig`, `StatusConfig`, `ProjectSettingsConfig`, `ProjectUrgencyConfig`, `AutoCompleteParentConfig`, `AutoRevertParentConfig`, `Role*` constants — all deleted
- `config.Validate` trimmed; business logic no longer lives in the config package
- `config/domain.go` (`WorkflowFromConfig` / `ProjectFromConfig` / `WorkflowID` / `ProjectID`) deleted

**Legacy Config Guard**
- `config.Load` hard-errors when the resolved file still contains `[projects.*]` or `[workflows.*]` sections
- Error message points users at `tusk project` / `tusk workflow` for replay
- Guard applies to `--config` paths, `TUSK_CONFIG`, walk-up hits, and the global config
- Embedded-defaults fallback is exempt (the embedded file is already trimmed)

**`tusk config show` Still Renders Projects and Workflows**
- DB-sourced `[projects.*]` and `[workflows.*]` sections with `# (from database — use …)` headers
- Deterministic name-sorted ordering
- JSON output emits a flat object with `storage`, `urgency`, `tui`, `mcp`, `projects`, `workflows` at the top level
- `tusk config get projects.<name>.<field>` / `workflows.<name>.<field>` resolves via service lookups
- `tusk config set projects.*` / `workflows.*` is rejected with a pointer to `tusk project modify` / `tusk workflow modify`
- MCP `tusk_config_set` matches the CLI rejection surface

**MCP Tools Route Through Services**
- `tusk_project_create / _modify / _delete` call `ProjectService`, accept and return `version` for end-to-end optimistic locking
- `tusk_workflow_create / _modify / _delete` call `WorkflowService`, same optimistic-locking contract
- The server-wide `configMu` mutex that used to serialize TOML writes is gone — SQLite + version checks replace it
- `ConfigReloadHook` plumbing removed from `internal/mcp/server.go` and `tui.New`

**Internal Package Cleanup**
- `inmem/` package **deleted** — it existed only because the TOML file was the source of truth
- `sqlite.SyncConfigToDB` **deleted** — migrations 003/004/006 seed the built-ins, making the sync path redundant
- `sqlitetest.NewStore(t)` simplified: no `cfg` parameter, relies on migration-seeded state
- `sqlitetest.SeedProject(t, repo, name)` helper added for tests that need an extra project
- `sqlitetest.KanbanConfig` / `KanbanWorkflow` deleted alongside `config.WorkflowConfig`

### Breaking Changes

- **`[projects.*]` and `[workflows.*]` are no longer valid TOML sections.** Any `tusk.toml` or `~/.config/tusk/config.toml` carrying them must have those sections removed and the equivalent entries recreated through `tusk project create` / `tusk workflow create`. Running `tusk` against a stale file produces a hard error pointing at the new commands. No silent migration is performed.
- **`tusk.Config.Workflows` and `tusk.Config.Projects` removed from the public library API.** Go programs that embed tusk via `tusk.NewClient(tusk.Config{…})` and previously passed `Workflows: …` / `Projects: …` must drop those fields. Fresh clients still come up with the built-in kanban workflow and `default` project via migrations; additional entries are created via `client.Projects.Create(...)` / `client.Workflows.Create(...)` at runtime.
- **`config.WorkflowConfig`, `config.ProjectConfig`, `config.StatusConfig`, and all supporting types are gone.** Any external Go consumer that imported them must switch to `domain.Workflow` / `domain.Project` (or the matching service inputs).
- **`sqlite.SyncConfigToDB` removed.** External code that called it to seed a workspace from a config struct must instead rely on migrations or call `ProjectRepo.Create` / `WorkflowRepo.Create` directly.
- **`inmem` package removed.** External code that imported `github.com/germanamz/tusk/inmem` for the in-memory project/workflow repositories must switch to the SQLite implementations.
- **`sqlitetest.NewStore` signature changed.** Tests calling `sqlitetest.NewStore(t, cfg)` must drop the `cfg` argument and use the new `SeedProject` helper if they need extra projects.
- **MCP server constructor lost the `ConfigReloadHook` parameter** and `tui.New` lost the matching `reloadHook` argument. Internal callers updated; external embedders must update too.
- **MCP `configMu` mutex removed.** Callers that relied on server-side mutex serialization for project/workflow writes should instead handle `domain.ErrConflict` returned from optimistic-locking checks.

### Usage

```bash
# Legacy file? Move project/workflow data to the database first.
# Before v0.10 upgrade:
tusk config show > backup.toml

# After upgrade:
# 1. Strip [projects.*] and [workflows.*] from your tusk.toml
# 2. Recreate via the CLI
tusk workflow create triage \
  status=new\(initial,start\) \
  status=investigating \
  status=resolved\(terminal,done\) \
  transition=new:investigating,investigating:resolved
tusk project create bugs workflow=triage urgency.priority_weight=8

# tusk config show still renders the full picture
tusk config show

# projects and workflows sections now come from the database
# config get still works for read access
tusk config get projects.bugs.urgency.priority_weight
tusk config get workflows.triage.statuses.new.roles

# writes route through the dedicated commands
tusk project modify bugs +urgency.blocking-weight=4
tusk workflow modify triage +status=review +transition=investigating:review

# config set rejects what it can no longer own
tusk config set projects.bugs.workflow kanban
# Error: projects.* is managed by the database — use `tusk project modify` instead
```

Agents hit the same surface via MCP:

```jsonc
// Create a project with optimistic locking
{ "name": "tusk_project_create",
  "arguments": {
    "name": "bugs",
    "workflow": "triage",
    "urgency": { "priority_weight": 8 }
  }
}
// Response includes version = 1

// Modify using the version returned by create/get
{ "name": "tusk_project_modify",
  "arguments": {
    "name": "bugs",
    "version": 1,
    "urgency_delta": { "blocking_weight": 4 }
  }
}
```

### Config Behavior

| Surface | Behavior |
|---|---|
| `config show` (text) | Storage/urgency/tui/mcp first, then DB-hydrated `# workflows (from database …)` and `# projects (from database …)` sections |
| `config show` (JSON) | Single flat object, DB-sourced `projects` and `workflows` at the top level |
| `config get projects.<name>.<field>` | Routes through `ProjectService.GetByName` |
| `config get workflows.<name>.<field>` | Routes through `WorkflowService.GetByName` |
| `config set projects.*` | Rejected with pointer to `tusk project modify` |
| `config set workflows.*` | Rejected with pointer to `tusk workflow modify` |
| `config set storage.*` | Unchanged — CLI writes to file, MCP rejects |
| `config set urgency.*` / `tui.*` / `mcp.*` | Unchanged — writes to the resolved config file |
| Legacy `[projects.*]` / `[workflows.*]` in config file | Hard error at `config.Load` |

### Design Decisions

- **Projects and workflows are workspace data, not user configuration.** Tasks already lived in SQLite. Projects and workflows have the same lifecycle — they're created, modified, and deleted during normal use, not edited out-of-band in a text file. Moving them to the database closes the last "config file is the source of truth" gap.
- **JSON blobs for per-project settings and workflow statuses.** Dedicated columns were considered and rejected: project settings are read once per service call and written rarely, so decode cost is negligible. Promotion to columns is a follow-up if profiling proves otherwise.
- **Real foreign keys, not just service-layer guards.** `tasks.project_id → projects.id` and `projects.workflow_id → workflows.id` both have `ON DELETE RESTRICT`. The service-layer delete guard still runs first and produces friendlier error messages, but the FK is the safety net.
- **Default rows seeded by migrations, not by startup sync.** Migration 003 inserts the kanban workflow, migration 004 inserts `_default`, migration 006 renames it to `default`. A fresh database is fully usable without any startup-time config-to-DB synchronization.
- **`SyncConfigToDB` removed outright.** Once migrations handle seeding, the sync path is dead code for default installs. The only users it helped were those with `[projects.foo]` sections, and they're better served by the legacy-section hard error + a CLI replay than by a silent first-run sync.
- **Hard error on legacy config over auto-migration.** Pre-1.0 users are the target audience; a loud failure with a clear pointer to the fix is preferable to silently translating data in ways the user might not expect. A `tusk config migrate-legacy` command was considered and deferred.
- **`configMu` mutex deleted.** SQLite serializes writes at the engine level and optimistic locking surfaces conflicts as `ErrConflict`. The server-level mutex was only needed when the write target was a TOML file that has no native concurrency story. With the DB backend, two agents can modify different projects in parallel without blocking each other.
- **`tusk config show` keeps rendering projects and workflows.** Removing those sections from the display would force users to join three commands mentally for every status check — a regression in ergonomics. Rendering them from the DB at display time, clearly marked as read-only, preserves the v0.9 experience while enforcing the new write boundary.
- **View types for `config show` are hand-rolled, not aliases of `config.*`.** The first draft aliased the old config structs to reuse their JSON/TOML tags. That would have created a latent compile break as the config schema trim landed; fresh view types decouple display rendering from the schema lifecycle entirely.
- **`inmem` package deleted without replacement.** It existed to expose TOML-derived maps behind the repository interface. With DB-backed repositories as the primary implementation, the in-memory fallback has no consumer — tests switched to `sqlitetest.NewStore` and there's nothing left for `inmem` to serve.
