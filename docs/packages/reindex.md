# internal/reindex

Walks the workspace tree, parses every markdown file, validates against the manifest, runs behavior hooks, resolves refs, and upserts nodes + edges + drift rows in one pass. Powers `tusk reindex` and the `tusk_reindex` MCP tool.

## Public surface

- `Run(ctx, Config) (*Report, error)` — single entry point.
- `Config` — repos, manifest, behaviors, optional drainer hookup.
- `Report` — `Indexed`, `Removed`, `Skipped`, `WorkflowViolations`, `PropertyViolations`, `RefDangling`, `RefAmbiguous`, `RefTypeMismatch`, `RefCycle`, `RefHealed`, `EmbedSettingsRequeued`, `EmbedDeferred`.
- `HealRefDrift(ctx, WorkerConfig) (HealReport, error)` — re-resolves recorded ref drift after a sweep; the MCP drainer calls it after productive ticks.

## Skipped files

`Report.Skipped` counts every file acked without indexing, which mixes two cases. A file with no frontmatter or no `type` is simply not a node, and vaults rely on that for plain markdown. `Report.NotNodes` counts that subset, and the worker logs it at debug level only, so the summary lines read `3 skipped (2 not nodes)` and a fresh vault of plain notes doesn't print a warning per note. A file that fails for a fault is broken: frontmatter that does not decode, an edge value of the wrong shape (`ResolveEdges`), a sub-unit parse failure, or a reserved-id path (`#`, or a `reindex:` prefix). Each fault is logged as a warning naming the file. Only the faults are recorded, through `FileStateRepo.RecordSkip`, with the error text, and `tusk doctor` reports each as a `skipped-file` error. The record is cleared when the file indexes, vanishes before the worker reads it, parses as a non-node, or is tombstoned by the reaper. A file that indexed once and then broke keeps its last good node row; the record is what tells doctor so.

Recording skips is also why `edgeDerivationVersion` was bumped: a broken file is stamped live in `file_state` by the walk, so the mtime+size check never re-reads it, and the forced pass after an upgrade is what records files that were already broken.

## Notes

Ref resolution runs per file against the live index, so a file processed before its target has a node row records `ref_dangling` drift instead of an edge. The **ref-drift heal pass** makes this converge: after the sweep's drain, `Run` re-enqueues the file behind every ref-kind drift row and drains once more — by then every live file has a node row, so refs that dangled only for ordering reasons (fresh index) or because their target was created after the referencing file was last indexed resolve, write their edges, and clear their drift. Genuinely broken refs re-record drift and stay in the report. Async walks instead enqueue the drifted files for the background drainer, which heals after any tick that indexed something. Report ref counters reflect the post-heal end state of the pass.

**Sub-unit line ranges.** The worker numbers markdown units with `subunit.AssignLines` over the whole file, starting from `node.Node.BodyOffset`, under the manifest's `[workspace] line-numbering` scheme. The scheme the stored ranges were numbered with lives in meta under `line_numbering`. When the configured scheme differs, or the key is absent because the index predates line ranges, `Run` forces one full re-process pass and stamps the key once the pass succeeds. The sync diff rewrites only rows whose lines moved and never re-embeds, so the pass costs a re-parse. One mechanism covers both the upgrade fill and a later scheme change. A daemon that has not yet reloaded a changed `tusk.toml` renumbers with its old scheme until its manifest watcher reloads it; that also costs only a re-parse, and the next pass converges.

**Name-form wikilinks.** A link that names a file by name (`[[auth-rfc]]`) is stored as written, with its text in the edge's `link` column (#791). `DrainReindexQueue` ends with `index.ResolveLinks` whenever it indexed or dropped a file, and `Run` calls it again after the reap, so names resolve against the whole node set whatever order the files drained in, and a file reaped with nothing left to drain still re-resolves the names that found it. Body links re-resolve on every pass, so a changed `[workspace] link-case` takes effect on them at once; a ref property's `[[name]]` is resolved when its file is parsed, so meta records the setting under `link_case` and a change forces one full re-process. The edge-derivation version was bumped for the same change, so existing indexes re-derive every edge once and fill the `link` column.

**Heading links.** A link with a `#fragment` is looked up the same way (#808): its text goes in the `link` column, and `index.ResolveLinks` points it at the section whose heading it names, matched on the section row's `name_key`. Because that pass runs after every drain that indexed a file, renaming, adding or reordering headings in one note re-points every link into it without the linking notes being re-read. The edge-derivation version was bumped again so existing indexes fill section keys and the `link` column of fragment links.

**Block references.** A `[[note#^block-id]]` link resolves the same way, matched on the `name_key` of the unit a `^block-id` marker names (#819). Moving a marker re-points every link into it on the next pass. The edge-derivation version was bumped once more: markers leave unit text and standalone marker lines stop being units, so existing indexes re-parse once to drop those rows and fill block keys. That pass re-embeds each unit whose text loses a marker, once. After it, adding, renaming or moving a marker re-embeds nothing, since the marker is not part of the text a unit embeds.

**Default type.** The worker parses with `node.ParseContentFileAs` and the manifest's `[workspace] default-type` (`Manifest.DefaultType`), so with the key set a markdown file with no type of its own indexes as that type instead of counting as a non-node (#790). It never writes such a file: the unquoted-date self-heal is skipped for an adopted node, whose dates are canonical in the index only. Meta records the configured type under `default_type`; when it differs, `Run` forces one full re-process pass, because turning the key on or off changes which unchanged files are nodes and the incremental skip would never revisit them. The key is stamped after the pass succeeds. A file that stops parsing as a node while still on disk (its `type:` removed, or the default type turned off) has its rows dropped by the worker through `dropFileNode`, the reaper's delete-and-wake sequence, and counts under `Report.Removed`; before #790 such a node kept its row indefinitely.

**Path refs.** The worker replaces each page's `path_refs` rows right after its edges, with `node.PathRefs` over the file as read (see [`internal/pathref`](pathref.md)). Meta records a fingerprint of the path-ref configuration under `path_refs`: the pathref rules version plus each paths edge type with its `from` list and whether it declares `to` (a paths-only type reads its frontmatter values as paths). When it differs, `Run` forces one full re-process pass, so turning `paths = true` on or off, editing `from`, adding or dropping `to`, or upgrading to a binary with new rules converges every page; nothing re-embeds. A vault with no paths edge type fingerprints as empty, so an index from before path refs existed needs no pass. The key is stamped after the pass succeeds.

**Sub-units off.** With `[workspace] sub-units = false` the worker still runs the sub-unit sync, with no units, so every file it processes drops the sub-unit rows an earlier pass with sub-units on wrote. Their edges and embedding mappings go with them by FK cascade, the drain's `index.ResolveLinks` moves the links that resolved into them back onto their notes, and the embed drain's orphan GC reclaims their vectors. Before #827 the worker skipped the sync instead, and since the sync is the only code that deletes sub-unit rows, not even `--force` removed them. Meta records the setting under `sub_units` (`off`, or empty for on). When it differs, `Run` forces one full re-process, so a plain `tusk reindex` drops every file's units after the setting is turned off and fills them after it is turned back on. On is stored as empty, so an index from before the key needs no pass, while one already built with sub-units off gets the pass that cleans it up. The key is stamped after the pass succeeds. `RebuildConfig` carries the manifest for the same reason: without it a schema rebuild wrote no sub-units and recorded them as on.

**Schema changes.** A file's edges (body wikilinks, ref properties) and its property and workflow drift are derived from `[node-types]`, `[edge-types]` and `[behaviors]` when the worker parses it, and `index.ResolveLinks` only re-targets link edges that already exist. So after an edit to those tables the incremental skip left every unchanged file with what the old schema derived (#831). Meta records `Manifest.SchemaFingerprint` under `index.ManifestSchemaKey`; when it differs, `Run` forces one full re-process and sets `Report.SchemaChanged`, so a plain `tusk reindex`, `tusk reload --reindex` or `tusk_reload` converges with no `--force` and nothing re-embeds. The fingerprint hashes the whole tables with descriptions cleared: a field added later is covered without a list to keep in step with the worker, and a description edit costs no pass. An index from before the key gets one pass, which also heals whatever earlier schema edits left behind. The key is stamped after the pass succeeds. `path_refs` stays its own key, since it also tracks the pathref rules version; a paths edit changes both and still costs one pass. `tusk reindex` and `tusk doctor --reindex` bump the manifest epoch when `SchemaChanged` is set, because they loaded `tusk.toml` for the pass: a running `tusk mcp serve` reloads it instead of seeing the recorded schema differ from its own and re-deriving the vault under the old one on its next file event. A long-running process never bumps, since its manifest may be the stale one, and `tusk watch` doesn't watch the epoch, so it keeps its boot manifest until restarted.

**Date self-heal and lines.** Quoting an unquoted date rewrites the frontmatter, so the worker re-derives `BodyOffset` from the re-read bytes (the body is still a suffix of them). Without that, sub-unit and path-ref lines would count against the pre-heal file and could land a line early.

**Embedding settings changes.** After the walk, `Run` compares `embed.DocumentFingerprint` of the manifest's `[embeddings]` section with the value stored in meta (`embed.DocumentFingerprintKey`). On a mismatch it records the new fingerprint first, then re-queues every embeddable node (`EmbedQueueRepo.EnqueueAllEmbeddable`: file rows and non-section sub-unit leaves with a payload, revoking any lease a drainer holds on them), and reports the count as `Report.EmbedSettingsRequeued`. That order is what keeps concurrent drainers honest: a drainer built from the old settings sees the new fingerprint and stops (`embed.DrainConfig.Fingerprint`), and one already holding a row can't ack it once its lease is revoked. Enqueueing directly, rather than forcing a full re-process, works the same for the sync CLI pass and the MCP daemon's async walk, whose background drainer never forces.

A process whose loaded manifest no longer matches `tusk.toml` on disk (a daemon that wasn't reloaded after the file changed) logs a warning and does nothing, so it can't re-embed the vault back to its stale settings or overwrite the fingerprint another process recorded. An index with no stored fingerprint records it without re-embedding when every document setting is at its default and every stored vector uses the current vector key; otherwise it re-embeds. A side effect: a `model` change converges on the next reindex without `tusk reset`. `ApplyEmbeddingSettings` runs the same check without a walk (used by `tusk reload`). The check needs `Config.Manifest`, `Embedder`, `EmbedQueue`, and `EmbeddingRepo`, and is skipped when any is missing.

**Unreachable embedder.** When the embedding drain at the end of `Run` stops on an `embed.TransportError` (the backend refused the connection, timed out, or returned a 5xx), `Run` doesn't fail. The structural pass has already committed, so it records the error as `Report.EmbedDeferred`, logs a warning with the queued count, and goes on to stamp `index.LastReindexAtKey` and the markers above. The rows stay queued for the next drain. Before #787 the error returned early, so the markers were never stamped and every later pass without the backend re-processed every file. `tusk reindex` adds the queued count to its summary and exits 0 (`--strict-embed` exits 1, `--no-embed` wires no embedder), `tusk_reindex` returns it as `embed_error`, and `tusk watch` starts anyway.
