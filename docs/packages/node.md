# internal/node

Heart of the data layer. Parses markdown frontmatter, validates properties against the manifest, resolves `ref` properties + body wikilinks + HTML `<a href>` links into edges, and provides the write-side service used by both CLI commands and MCP tools.

## Public surface

- `ParseFile(relPath, content) (*Node, error)` — frontmatter → `Node` shape; ID is the relPath sans extension. `Node.BodyOffset` is the byte offset in `content` where `Body` starts (after frontmatter, leading blank lines, and any BOM), so sub-unit line numbers can count the whole file. An unquoted frontmatter wikilink (`assignee: [[people/jane]]`) decodes in YAML to a nested flow sequence, not a string; since no property type nests lists, `ParseFile` normalizes that exact `[[id]]` / `[[id|alias]]` shape back to the scalar string so it resolves like its quoted twin instead of dropping the whole file from the index (#692).
- `ParseFileAs(relPath, content, fallbackType)` / `ParseContentFileAs` — as `ParseFile` / `ParseContentFile`, but a markdown file with no type of its own (no frontmatter, or frontmatter without `type:`) is adopted as `fallbackType` instead of failing with `ErrMissingFrontmatter` / `ErrMissingType` (#790). The adopted node keeps any frontmatter the file has, sets `Node.Adopted`, and takes its title from `title:`, else the first level-one heading (`subunit.FirstHeading`), else the file name. With no frontmatter the whole file, less a BOM, is the body. HTML is never adopted. An empty fallback adopts nothing.
- `Service` — `Create`, `Modify`, `Move`, `Delete`; serialized via the workspace lock. `Create` and `Modify` write through the `file_state` lease, so the next reindex skips the page. Each one therefore leaves the index as a re-parse of the written bytes would: the node row, its edges, its path refs, and its sub-units. The sub-unit pass is the reindex worker's markdown one (`subunit.Parse`, `AssignLines`, `Sync.ApplyFile`), so new pages get sub-units, a new body replaces the old ones, and a frontmatter edit renumbers their lines (#782). `ServiceDeps.Manifest` drives it; `DepsFromIndex` sets it, and nil skips it.
- `ValidateProperties(*Node, NodeTypes) PropertyResult` — type / required / drift checks.
- `ResolveEdges(*Node, EdgeTypes) error` — frontmatter edge values → typed edges. Under a paths-only edge type (`EdgeType.PathsOnly`) whose `from` allows the page, a value is a workspace path instead: it goes to `Node.PathValues` for `PathRefs`, never to `Node.Edges`. A value `pathref.Declared` rejects stays an edge.
- `ResolveRefs(*Node, NodeTypes, RefLookup) RefResolutionResult` — refs + wikilinks → resolved edges. A wikilink value resolves the way a body link does (`wikilink.Resolve`): a path as written, a relative path from the node's folder, a name through the lookup's `wikilink.Files` half. A name two files share is `ref_ambiguous` with both listed (#791).
- `MaterializeWikilinks(*Node, EdgeTypes)` — appends the body wikilinks [`internal/wikilink`](wikilink.md) extracts to every edge type declared with `wikilinks = true`. Replaces the former hardcoded `references` special case; the name of the target edge no longer matters and zero, one, or many edges may opt in. Called by both `Service` and the reindexer. The Obsidian aliased form `[[id|display]]` (and `[[id#S1|display]]`) links to `id`; the text after the first `|` is display only and is dropped for edge derivation and ref resolution, but preserved verbatim when a `tusk node move` rewrites the link on disk. A relative target is stored as the id it names; a name (`[[auth-rfc]]`) is stored as written and listed in `Node.NameLinks`, so its row carries the link text for `index.ResolveLinks` to resolve once every file is known (#791).
- `EdgeRows(*Node, NodeTypes) []index.EdgeRow` — the one conversion from `Node.Edges` to index rows, used by every writer of a file's content edges (the reindexer included). Ref properties are `derived`, everything else `direct`. A direct frontmatter value written as a wikilink (`relates-to: "[[auth-rfc|RFC]]"`) is unwrapped like a body link; before #791 the brackets were stored as part of the target, so the edge always dangled.
- `ResolveHTMLLinks(sourcePath, hrefs) []string` — turns an HTML node's raw `<a href>` values (collected into `Node.HTMLLinks` by `ParseHTMLFile`) into target node ids, resolving each path-relative href against the source file's directory. HTML node ids retain their extension, so `href="topic-map.html"` from `mml/index.html` resolves to `mml/topic-map.html`. Drops external URLs, protocol-relative links, in-page anchors, and links that escape the vault root; strips query/fragment; unique in first-seen order. The resolution is `pathref.Link`'s, shared with path refs.
- `MaterializeHTMLLinks(*Node, EdgeTypes)` — the HTML counterpart of `MaterializeWikilinks`: appends resolved `<a href>` targets to every `wikilinks = true` edge type. A no-op for markdown nodes (no `HTMLLinks`). Called by the reindexer, the path that indexes dropped-in HTML files.
- `PathRefs(*Node, file, EdgeTypes, linenum.Scheme) []index.PathRefRow` — the path refs a page records, once per edge type that sets `paths = true` and lists the page's type in `from`: the paths its body names (markdown code spans, links and images; HTML `<code>` outside `<pre>`, `<a href>` and `<img src>`, collected into `Node.HTMLCode`, `Node.HTMLLinks` and `Node.HTMLImages` by `ParseHTMLFile`), plus, under a paths-only type, its frontmatter values from `Node.PathValues` with the lines they are written on. `ResolveEdges` must have run. `file` is the whole file, so markdown lines count from its top. The rules live in [`internal/pathref`](pathref.md). The reindexer calls it for every page, and the service re-derives a page's refs wherever it rewrites the page's edges (create, modify, `ReindexSource`), because those writes stamp `file_state` and the next reindex skips the file. `Rename` re-derives the moved page's refs at its new path, since a relative link can name another path from there, and re-derives each referrer it rewrites, since a retargeted HTML href is a ref too. It leaves paths-only frontmatter values in referrers as written.
- `AddEdgeToFrontmatter(root, sourceID, sourceType, edgeType, targetID, edgeTypes, nodeTypes) error` — inserts an edge target under the edge-type key in the source's frontmatter, respecting cardinality (scalar for one-to-one / many-to-one; list for one-to-many / many-to-many). Atomic read-mutate-write; callers must hold the workspace lock.
- `RemoveEdgeFromFrontmatter(root, sourceID, sourceType, edgeType, targetID, edgeTypes, nodeTypes, files) error` — idempotent inverse; drops the key when the last target is removed. A value written as a wikilink matches when it names `targetID` the way its edge does, so an edge `tusk edge list` shows can be removed by the id it shows. Both take the source's indexed type as the parse fallback for an adopted file, which also picks the layout an unquoted date is re-emitted in.
- `ReindexSource(root, nodes, edges, refs, edgeTypes, nodeTypes, sourceID, lineNumbering, linkCase) error` — re-parses the source file and upserts its resolved edges and path refs into the index under the source's real path, then resolves name-form links. Used by `tusk edge add` / `tusk edge remove` to refresh the index after a frontmatter rewrite without waiting for the watcher.

## Notes

Only reindex reads `[workspace] default-type`: it decides which untyped files are nodes. Every later re-parse of an indexed file (`Get`, `Modify`, the edge writers, `ReindexSource`, `Rename` and its referrers, the path-ref sync, the embed drain) passes the type the index already holds for the file as the fallback (the file node's type, even when the call names one of its sub-units), so an adopted file parses the same way everywhere without the manifest being threaded through. No writer adds a type to an adopted file: `renderMarkdown` emits no frontmatter block when there are no properties, so a body-only `Modify` keeps a plain file plain, and a property or edge write adds frontmatter without `type:`.

`ResolveRefs` falls back from `Properties` to `Edges` because `reindex.go` reorders the pipeline (`ResolveEdges` runs first there). `Service.Create` runs `ResolveRefs` before `ResolveEdges` to avoid the fallback. Two code paths with different value-source assumptions — handoff §residual to clean up by re-ordering reindex's pipeline.

Every writer of name-form links resolves them before it returns: `Create`, `Modify`, `ReindexSource`, `Delete` and `Rename` call `index.ResolveLinks` with the manifest's `link-case`, since each either stores a link as written or changes which files a name can find. `Delete` and `Rename` take the `linkCase` as a parameter for that.

`Rename` judges every link by what it named before the move and what it would name after (`linkMove`, built from two `wikilink.Names` snapshots), so a move never breaks or redirects a link. A path to the moved note takes the new id. A relative link is re-rendered from where its file lives after the move, including the moved note's own links, which were written from its old folder. A name stays as written while it still finds the same note; when it no longer does, it becomes the note's new name if that alone finds it, and the full id otherwise. The files that link by name to another note the moved one now shares a name with are rewritten too (to that note's full id) and reported in `AffectedFiles`. The rewrite re-derives only file-level rows, so `index.EdgeRepo.RenameLink` carries each renamed link text onto the sub-units' rows and the moved note's re-based rows.

The wikilink scanner lives in [`internal/wikilink`](wikilink.md), which also documents why a link inside code is not a link: `MaterializeWikilinks` derives no edge from it, and a `tusk node move` leaves it as written (#788). It moved out of this package so `internal/subunit` no longer imports `node`, which lets the service run the sub-unit pass itself.
